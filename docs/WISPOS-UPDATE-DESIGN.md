# WispOS on-device OS updates: design

Written 2026-10-11 (effort 2 of "Remaining efforts before 0.1.0", docs/WISPOS-OS-DESIGN.md). Status: **the D-Bus half exists and is tested** (`os/steamos/wisp-steamos-manager.c`, docs/WISPOS-STEAMOS-CONTRACT.md); **the helper, the package format, the apply step and the rollback do not exist yet**. Items marked DECISION need the operator.

## Requirements (operator's words and standing rules)
- Updates through **Steam's own System Update screen** (the way Bazzite and SteamOS do it): Steam asks `com.steampowered.Atomupd1`, we answer.
- **"No host of ours"** (binding): the update files and the manifest live on an upstream origin we do not operate. The natural fit is GitHub Releases of this project.
- Write to the SD card as little as possible (2026-10-11): one staged copy per update, nothing else, no polling logs.
- Never reboot unattended; a half-applied update must never leave a card that cannot boot without a PC.

## What is on the card (verified in `os/build-image.sh`, the built SYSTEM and ROCKNIX's init)
- Boot partition (FAT, label ROCKNIX, **1 GiB**): `KERNEL` (33 MB: the kernel with the initramfs inside it), `SYSTEM` (180 MB squashfs), `dtb.img`, `overlays/`, `extlinux/extlinux.conf`, `wispos/`. Mounted **read-only** at `/flash` in the running system.
- The initramfs mounts `/flash/SYSTEM` as the root (loop, ro). The modules in SYSTEM must match the kernel's release (CRCs differ between builds), so **KERNEL and SYSTEM always change together**.
- ROCKNIX's own updater (in the initramfs `init`, lines ~860-1135): looks in `/storage/.update` for a tar, checks `.md5` files, checks the new SYSTEM's `os-release` against the old (`HW_DEVICE`, `HW_ARCH`), checks free space, then **overwrites `KERNEL` and `SYSTEM` in place with `dd`** and reboots. In place means a power cut in the middle leaves a corrupt file: not acceptable here. Its tar name must also contain "ROCKNIX". We do not reuse it.
- Room: current 213 MB + staged new 213 MB + the kept old 213 MB fits in 1 GiB with about 350 MB spare.

## Design
**1. Manifest** (one small JSON, an asset of the latest GitHub Release, fetched from the stable `.../releases/latest/download/manifest.json`):
`{ "format": 1, "variant": "stable", "build_id": "20261012.1", "version": "0.1.1", "requires": "0.1.0", "update_type": 0, "hw_device": "H700", "files": { "KERNEL": {"url": ..., "size": N, "sha256": ...}, "SYSTEM": {...} } }` plus a detached **ed25519 signature** over the manifest bytes (`manifest.json.sig`). The device verifies the signature with a public key baked into the image (`/usr/share/wispos/update-key.pub`), then each file's size and sha256. `openssl` (3.x, in the image) does ed25519 (`pkeyutl -verify -rawin`); curl and python3 are there too. A key rotation is an update signed by the old key that ships the new one. **Hosting (operator, 2026-10-11): GitHub, the repository that hosts the OS** (public: the device fetches without credentials; no remote exists for this repository yet, and creating or publishing it is the operator's act). The signing key pair exists now: public half `os/steamos/update-key.pub` (committed, baked into every image), private half `~/.wispos-release/update-signing.pem` on the build host, mode 0600, outside the repository (back it up; `os/make-release.py keygen` never overwrites it). `os/make-release.py build` produces the four release assets and the signed manifest; the device finds the manifest at `https://github.com/OWNER/REPO/releases/latest/download/manifest.json`, so the URL goes into `os/steamos/update-source.json` once OWNER/REPO is settled.

**2. `wisp-update` (the helper the daemon runs; Python, stdlib + the openssl and curl binaries, resident only while it runs).** The protocol it speaks is already fixed and tested in the daemon (`check`: `update`/`later` lines; `apply ID`: `progress`, `done`, `error`):
- `check`: fetch + verify the manifest; compare `build_id` with the running one (`WISPOS_BUILD_ID` in os-release); same `hw_device`; `requires` newer than what runs goes out as `later`. Nothing is written to the card.
- `apply ID`: remount `/flash` read-write (only now), download `KERNEL.new` and `SYSTEM.new` into `/flash/wispos/update/` with resume (Range requests, so Pause/Resume and a Wi-Fi drop cost nothing), verify sizes and hashes, `sync`, write the marker `/flash/wispos/update/READY` last, remount read-only, report `done`. SIGTERM (cancel) deletes the partial files first. Free space is checked before the first byte.
- It never reboots by itself. The UI then offers the restart (Steam's own "restart to apply"); **how Steam asks for the reboot is to be captured once the interface answers** (the contract document lists it as unknown).

**3. Apply at the next boot, inside our initramfs** (the initramfs is ours to patch: `os/boot/patch_initramfs.py` already replaces exactly one entry; this adds one hook before the SYSTEM mount). If `READY` exists: `KERNEL` -> `KERNEL.old`, `SYSTEM` -> `SYSTEM.old`, `KERNEL.new` -> `KERNEL`, `SYSTEM.new` -> `SYSTEM` (FAT renames are directory-entry updates, each one sector), write `wispos/update/PENDING`, delete `READY`. The splash says "Installing the update" (the init feeds it through the FIFO). A power cut at any point is recoverable: before the renames nothing changed; between them the init finishes the sequence from the marker files on the next boot (each step is idempotent and checks which of the four files exist).

**4. Confirmation and rollback.** The new system, once the Steam session has reached its UI (the watchdog already knows), deletes `PENDING` (a write of one directory entry). If the next boot finds `PENDING` still present, the previous boot did not reach the UI: the initramfs swaps `.old` back (both files) and boots that, leaving `FAILED-<build_id>` behind so the update is not offered again until a newer one exists. This covers a new SYSTEM that boots but fails. **It does not cover a new KERNEL that does not boot at all** (no initramfs runs, so nothing can swap): U-Boot's own boot-count fallback would, but that is a U-Boot rebuild (our U-Boot is built from source, so it is possible); until then the recovery is documented and manual (card in a PC, rename `*.old` back). **DECISION: is "SYSTEM + KERNEL with initramfs-level rollback, manual recovery for a dead kernel" enough for 0.1.0, or does 0.1.0 wait for the U-Boot fallback?** My recommendation: ship the former, because a kernel change is the rare case, and put the U-Boot fallback on the 0.2 list.

**5. Identity the running system reports.** `os-release` must carry `WISPOS_VERSION` (the manifest version) and `WISPOS_BUILD_ID` (`YYYYMMDD.N`, comparable). Today the image has `WISPOS_VERSION="0.1.0-dev"` and ROCKNIX's `BUILD_ID` (a git hash), so the daemon reports the version and an unusable build id until `stage_rootfs.py` stamps `WISPOS_BUILD_ID` from the release (the build-identity item of effort 1/4).

## How Steam's UI reaches this (measured on the device 2026-10-11; supersedes the paragraph below)
With `-steamos3` (alone: `-steamdeck` is not needed) Settings > System > Software Updates runs the script `/usr/bin/steamos-polkit-helpers/steamos-update`: `check` exits 0 when an update is available and 7 when not, the install call prints `NN%` progress lines and exits 0, after which Steam says "system restart required" and offers Restart. **`os/rootfs/usr/bin/steamos-polkit-helpers/steamos-update` implements exactly that over `wisp-update`** (tests in `os/test_steamos_scripts.py`); `Atomupd1` is not what the UI calls. Open: (a) the Restart button's own command (Steam names `steamos-reboot` and `steamos-reboot-other`; not implemented, to find by pressing Restart once the image has the helpers), (b) the standing warning mark: in this mode Steam logs `Client version: 0` and believes a client update is always pending, so "Apply" never goes away; where it reads the installed client version in this mode is unresolved and decides whether `-steamos3` ships without a permanent warning on the gear.

## What Steam's UI will show (older paragraph, kept for the record)
Today Steam only calls `Atomupd1.DisableHttpProxy()` at start (measured). Whether the System Update page and its "Check for updates" button appear depends on Steam's SteamOS switches (`-steamos3 -steamdeck`; the shipped command line has neither). That is the open question of the UI, not of the daemon: test it with `os/dev/steam-args.sh` once `wisp-update check` returns something real, then decide the command line for the release (it also changes the gear icon and the performance menu).

## Tests this needs (before any of it ships)
- `wisp-update`: manifest verification (good, tampered, wrong key, wrong hash, truncated, replayed older build), resume, cancel cleanup, free-space refusal: host tests with a local HTTP server and a throwaway key.
- The initramfs hook: QEMU boots with a staged update, with a power cut injected between each rename (kill QEMU at each step), and the rollback path; the existing `qemu_splash_test.py` machinery is the base.
- The D-Bus side is done (30 tests against Valve's XML); add a QEMU check that a real `check` reaches a local manifest.

## Order of work
1. Operator decisions above (repository/hosting, signing key, rollback depth).
2. `wisp-update check` + tests, os-release stamping, Steam UI test (the capture tells us what Steam really calls).
3. `apply` + the initramfs hook + QEMU power-cut tests.
4. A release produced by CI-less local tooling and published as a GitHub Release by the operator (we do not publish anything ourselves).
