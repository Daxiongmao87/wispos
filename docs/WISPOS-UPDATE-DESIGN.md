# WispOS on-device OS updates: design

Written 2026-10-11 (effort 2 of "Remaining efforts before 0.1.0", docs/WISPOS-OS-DESIGN.md); **amended 2026-10-12: the apply step is a switch between two boot slots, not renames** (see "Amendment" below). Status: **built and tested on the host and in QEMU, never run on the hardware** (device checklist in docs/WISPOS-NOTES.md "Next device session"). The pieces: the D-Bus half (`os/steamos/wisp-steamos-manager.c`, docs/WISPOS-STEAMOS-CONTRACT.md), the helper `os/steamos/wisp-update` (`check`, `apply`, `confirm`, `status`), Steam's script `steamos-update`, the initramfs step `os/boot/wisp-boot.sh`, the trial-confirming unit `wisp-update-confirm`, and the release tool `os/make-release.py`. Items marked DECISION need the operator.

## Requirements (operator's words and standing rules)
- Updates through **Steam's own System Update screen** (the way Bazzite and SteamOS do it): Steam asks, we answer.
- **"No host of ours"** (binding): the update files and the manifest live on an upstream origin we do not operate. The natural fit is GitHub Releases of this project.
- Write to the SD card as little as possible (2026-10-11): one staged copy per update, nothing else, no polling logs.
- Never reboot unattended; **a half-applied update must never leave a card that cannot boot without a PC.**

## What is on the card (verified in `os/build-image.sh`, the built SYSTEM and ROCKNIX's init)
- Boot partition (FAT32, label ROCKNIX, **1 GiB**), mounted **read-only** at `/flash` in the running system: `KERNEL` (33 MB: the kernel with the initramfs inside it), `SYSTEM` (180 MB squashfs), `dtb.img`, `overlays/`, `extlinux/extlinux.conf`, `wispos/`.
- The initramfs mounts the system image as the root (loop, ro). The modules in SYSTEM must match the kernel's release (CRCs differ between builds), so **KERNEL and SYSTEM always change together**. The device tree, the overlay and the kernel command line are **not** part of an update (they are shared by both slots and pinned by the lock file, `os/verify_image.py`); a release that needs a different one is a re-flash release (DECISION to revisit when a release first needs it).
- ROCKNIX's own updater (in the initramfs `init`) looks in `/storage/.update` for a tar and overwrites `KERNEL` and `SYSTEM` **in place with `dd`**: a power cut leaves a corrupt file. Not acceptable here; we do not use it (and nothing puts a tar there).
- Room: two systems are 426 MB; the card has about 600 MB free after them, so a download needs no third copy.

## Amendment 2026-10-12: why two slots and not renames
The first plan (this document, 2026-10-11) staged `KERNEL.new`/`SYSTEM.new` and let the initramfs rename `KERNEL`→`KERNEL.old`, `.new`→`KERNEL` at the next boot. **That plan had a window in which the card has no `KERNEL`** (between the two renames). A power cut there leaves U-Boot with nothing to load, and the initramfs that was supposed to finish the job is inside the missing file. The text claimed "recoverable at any point"; it was not. Found while writing the apply step; no image ever shipped it. It also needed a second restart (the renames happen under the OLD kernel). The slot scheme below has no such window, needs no extra restart, and lets the helper do all the writing in the running system.

## Design
**1. Manifest** (one small JSON, an asset of the latest GitHub Release, fetched from the stable `.../releases/latest/download/manifest.json`):
`{ "format": 1, "variant": "stable", "build_id": "20261012.1", "version": "0.1.1", "requires": "0.1.0", "update_type": 0, "hw_device": "H700", "files": { "KERNEL": {"url": ..., "size": N, "sha256": ...}, "SYSTEM": {...} } }` plus a detached **ed25519 signature** over the manifest bytes (`manifest.json.sig`). The device verifies the signature with a public key baked into the image (`/usr/share/wispos/update-key.pub`), then each file's size and sha256. `openssl` (3.x, in the image) does ed25519 (`pkeyutl -verify -rawin`). A key rotation is an update signed by the old key that ships the new one. **Hosting (operator, 2026-10-11): GitHub, the repository that hosts the OS** (public: the device fetches without credentials; creating or publishing the repository is the operator's act). The signing key pair exists: public half `os/steamos/update-key.pub` (committed, baked into every image), private half `~/.wispos-release/update-signing.pem` on the build host, mode 0600, outside the repository (back it up; `os/make-release.py keygen` never overwrites it). `os/make-release.py build` produces the four release assets and the signed manifest; the device finds the manifest at `https://github.com/OWNER/REPO/releases/latest/download/manifest.json`, so the URL goes into `os/steamos/update-source.json` once OWNER/REPO is settled.

**2. Boot slots.** The card holds two complete systems: **slot a** is `/KERNEL` + `/SYSTEM` (what the image ships), **slot b** is `/wispos/b/KERNEL` + `/wispos/b/SYSTEM` (empty until the first update). `extlinux/extlinux.conf` has two labels, `a` and `b`, that differ only in the kernel path and in `wisp.slot=a|b` on the command line, and its **first line, exactly `DEFAULT a` or `DEFAULT b`, says which one U-Boot starts**. Switching is changing that one letter **in place** (one byte of one sector: nothing renamed, nothing truncated), so at every instant the card names a slot that is whole. From U-Boot's source in our build (`boot/pxe_utils.c`, `common/menu.c`): no `PROMPT`/`MENU`/`TIMEOUT` means `menu_get_choice` returns the default without asking; and when the default label's kernel cannot be *loaded* `handle_pxe_menu` falls through to `boot_unattempted_labels`, which tries the other label. The running slot is known from `wisp.slot=` in `/proc/cmdline` (none: a). The initramfs mounts the slot's own system image (`IMAGE_SYSTEM`).

**3. `wisp-update` (Python, stdlib + the openssl binary, resident only while it runs).** The protocol it speaks to the daemon is fixed and tested (`check`: `update`/`later` lines; `apply ID`: `progress`, `done`, `error`):
- `check`: fetch + verify the manifest; compare `build_id` with the running one (`BUILD_ID` in os-release); same `hw_device`; `requires` newer than what runs goes out as `later`; **a build the card sent back (`FAILED-<build_id>`) is not offered again**. Nothing is written to the card.
- `apply ID`: refuses while a trial is running or an earlier update waits for its restart (the other slot is then the only way back); targets the slot that is NOT running; remounts `/flash` read-write (only now); downloads `KERNEL.part`/`SYSTEM.part` into that slot with resume (Range requests, so Pause/Resume and a Wi-Fi drop cost nothing), verifies size and sha256, replaces the slot's file in one rename (the slot is not running, so a half-way state is harmless), reads both files back **from the card** (cache dropped) against the signed hashes, then **commits in a fixed order: (1) write `/wispos/update/PENDING` (slot, build_id, version, tries=0), (2) flip the letter**; `sync`; remount read-only; report `done`. SIGTERM (cancel) deletes the partial files first. A file the slot already holds is not downloaded again (an interrupted earlier try). Free space is checked before the first byte.
- `confirm`: if `PENDING` names the running slot, delete it (the trial ends). `status`: what the card says.
- It never reboots by itself. Steam then offers Restart.

**4. Trial, confirmation, rollback** (`os/boot/wisp-boot.sh`, a boot step added to ROCKNIX's init between `cleanup_flash` and `mount_sysroot`; `os/boot/patch_initramfs.py` adds the file and two lines to `/init`, refusing an init that lacks either anchor exactly once):
- `PENDING` names the slot being started: **the new version is on trial**. Each start counts (`tries` 0→1→2). The running system ends the trial with `wisp-update confirm`, called by `wisp-update-confirm.service` (only started when `PENDING` exists) once the compositor **and** a session program (Steam, the first-run setup or the desktop) have been active together without a gap for 90 s.
- A start that finds `tries` already at 2 means the version did not come up well twice: the initramfs writes `FAILED-<build_id>` (first, so that whatever happens next the build is not offered again), flips the letter back, deletes `PENDING`, and restarts. The previous version's own kernel then boots with its own system. If the other slot is not whole, or `extlinux.conf` is not in the expected form, nothing is written and the boot carries on.
- `PENDING` for the OTHER slot is stale (the switch was never made, or was undone): removed.
- **Why this is power-cut safe:** the sequence is staged files → `PENDING` → letter, each durable before the next, and the rollback is `FAILED` → letter → delete `PENDING` → restart. A cut after any step leaves a card whose named slot is whole, and the next boot's rules converge (tests below cut at every sync of every sequence, on the host and in QEMU).
- **No hands needed for the failures the initramfs can see (2026-10-12):** once the start is counted (durably), `wisp_trial_guard` replaces the reference init's `error` (a debug shell nobody can type into: "Could not find systemd!") and `poweroff` (a system image that will not mount) by a restart, so a broken new system walks through its three starts on its own. A kernel panic restarts after 10 s (`panic=10` on both labels, checked by `verify_image.py`). A system that boots but never becomes healthy is restarted by `wisp-update-confirm` after 10 minutes. Outside a trial the reference behaviour is unchanged. Tested in the three shells of `os/test_boot_slots.py` (+4 mutants) and, with the real initramfs, in QEMU (`rollback`: a system that cannot be mounted; `nosystemd`: one that mounts and has no init).
- **A new KERNEL that dies before its initramfs runs (2026-10-12, operator's choice of U-Boot's own counter):** the initramfs cannot count what never reaches it, so the bootloader counts. `os/boot/uboot/wisp-trial.txt` is compiled into the handheld's U-Boot (`install_env.py` adds `WISP_ENV` after `BOOTENV` in `sunxi-common.h` and redefines the distro boot's `boot_extlinux` to run it first; `build-uboot.sh` checks the default environment has both, in that order). Before it starts extlinux it reads byte 8 of `extlinux.conf` (the letter) and `wispos/update/PENDING`; while the letter names the slot the marker names, every start adds one to `wispos/update/BOOTS` (`fatwrite`, a small file; `boot_tries=N`). The initramfs of the trial slot deletes `BOOTS` the moment it runs, so only starts that never got there accumulate. Finding `BOOTS` at 2, U-Boot starts `extlinux/rollback.conf` (the same two labels, `DEFAULT a`, written by `build-image.sh`, never edited by an update) instead; slot a's initramfs sees the letter naming a version on trial while it is the one running, writes `FAILED-<id>`, flips the letter back to a and removes `PENDING` and `BOOTS` (the same bookkeeping covers a kernel U-Boot could not load at all). `wisp-update apply` and `confirm` delete `BOOTS` too, so a trial always starts from zero. U-Boot never writes `extlinux.conf` (a FAT rewrite is not atomic and that file is the boot); any step that fails leaves the normal boot to carry on. **A dead kernel restarts nothing: the person power-cycles the handheld, twice, and the third start is the previous version** (a hardware watchdog armed by U-Boot would make that automatic; not built, because none of it can be tried on the host). Tested: the script by the real U-Boot interpreter (`os/test_uboot_trial.py`, the sandbox build of the handheld's own source tree, a real FAT image, `fsck.fat` after the writes; 15 mutants), the initramfs half in three shells (`os/test_boot_slots.py`), the hook's presence in the compiled default environment (build-time check). NOT tried: the script on the H700 itself (the only real-hardware link is that `sunxi` U-Boot's `fatwrite` to the SD card works, as its `saveenv` to FAT does).
- **What it does not cover:** a card whose FAT is damaged by a power cut during one of U-Boot's small writes (the count file; a FAT rewrite is not atomic), and anything that stops before U-Boot's script runs (boot ROM, SPL, DRAM setup: not part of an update). Recovery for those: any computer, any text editor, first line of `extlinux/extlinux.conf`, `DEFAULT b` → `DEFAULT a` (printed in `wispos/README.txt` on the card), or a re-flash.

**5. Identity the running system reports.** `os-release` carries `BUILD_ID` (`YYYYMMDD.N`, comparable; from `WISP_BUILD_ID` at build time, else the build date) and `WISPOS_VERSION` (stage_rootfs.py; the release process sets 0.1.0). The daemon reports them as Atomupd1's `CurrentBuildID`/`CurrentVersion`.

**6. Trying an update before anything is published (dev images only).** A dev image (`/usr/lib/wispos/DEV-BUILD` exists in its SYSTEM; `os/check_rootfs.py` fails a release tree that has it) also reads `/storage/.config/wispos/update-dev.json`, `{"manifest_url": "http://HOST:PORT/manifest.json", "allow_http": true}`: the URL replaces the image's own source and `allow_http` (exactly `true`) lets plain http through. Nothing else changes: the manifest is still verified against the key baked into the image and every file against its hash, so what travels over http cannot change what is installed. A release image never looks at the file; `wisp-update status` says `source URL` while the override is in use. The host side is `os/dev/test-release.sh`: it copies the candidate's SYSTEM with `/etc/os-release` stamped as the next build and version (nothing else differs: tested file by file), signs a manifest for it with the REAL release key (the one the images trust, kept outside the repository) and serves the directory with `os/dev/serve_release.py` (Range requests, so Pause/Resume and a Wi-Fi drop are exercised too). `--broken` removes the new system's init, so the initramfs stops at "Could not find systemd" and the card must return to the old slot by itself after the three starts: the rollback on the real hardware, on purpose.

## How Steam's UI reaches this (measured on the device 2026-10-11)
With `-steamos3` (alone: `-steamdeck` is not needed) Settings > System > Software Updates runs the script `/usr/bin/steamos-polkit-helpers/steamos-update`: `check` exits 0 when an update is available and 7 when not, the install call prints `NN%` progress lines and exits 0, after which Steam says "system restart required" and offers Restart. **`os/rootfs/usr/bin/steamos-polkit-helpers/steamos-update` implements exactly that over `wisp-update`** (tests in `os/test_steamos_scripts.py`); `Atomupd1` is not what the UI calls. The **Restart** button: Steam's binaries name `steamos-reboot`; **`steamos-polkit-helpers/steamos-reboot` is added (plain `systemctl reboot`)**; whether that is the exact name and call form Steam uses for this button is unverified until it is pressed on the device (checklist). Still open: the standing warning mark on the gear in `-steamos3` mode (Steam logs `Client version: 0` and believes a client update is always pending); where it reads the installed client version in this mode is unresolved and decides whether `-steamos3` ships without a permanent warning.

## Tests
- `os/test_wisp_update.py` (61 + 25 mutants, 6.5 min): the helper against a local HTTP server with a throwaway key on a fake card — signature, newer-only, resume, cancel, hash and size failures, read-back from the card, free space, which slot is targeted, refusals while a trial runs, the commit order, **a cut after each commit step (`WISP_UPDATE_STOP_AFTER`)**, `confirm`, `status`, and `BootContract`: the real boot step run in dash on what the helper wrote (an update starts on trial, confirms; one that never confirms is sent back and not offered again; the second update goes into the first slot).
- `os/test_boot_slots.py` (20 scenarios × dash, bash --posix and **the initramfs's own busybox under qemu-user**, + 20 mutants): the boot step on a fake card, including a **stop at every sync of every sequence** followed by the boots the card then asks for.
- `os/test_initramfs.py`: the patched archive differs from ROCKNIX's reference in four entries only; `/init` gets exactly two lines.
- `os/test_dev_release.py` (7 + 5 mutants): the dev tooling for §6 on a synthetic SYSTEM: the restamped copy differs in `/etc/os-release` only, the broken one lacks the init and nothing else, ids are validated before anything is deleted, the REAL helper installs the result on a fake dev image over plain http and a fake release image does not try, the server answers Range requests and serves nothing outside its directory.
- `os/test_update_confirm.py`: the confirm unit's script and wiring. `os/test_fatwrite.py`, `os/test_qemu_update_harness.py`: the FAT writer (now nests) and the QEMU harness's own reader.
- `os/qemu-update-test.sh` (`os/boot/qemu_update_test.py`): the real initramfs, busybox, vfat driver and helper in QEMU with a stand-in for U-Boot that reads the card's media: a real-size update, restart into slot b, trial counted, confirm; a payload that cannot start rolled back after three starts; power cuts (SIGKILL) after each commit step.
- Not testable here: real U-Boot on the H700 (its label selection is read from the source above, not run), a card that loses writes, the SD card's behaviour on a power cut at the sector level, Steam pressing Restart.
