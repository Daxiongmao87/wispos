## 2. How to work with the device (no reflash needed)

### 2.1 Reaching it
- It announces itself to the listener on this machine: `python3 os/dev/listen.py` (port 47653, state `~/.wispos-dev/devices.json`).
  Address was 192.0.2.110 (DHCP, may change; MAC 68:8f:c9:52:2d:3c).
- `ssh -i ~/.ssh/wispos-dev -o IdentitiesOnly=yes -o BatchMode=yes -o UserKnownHostsFile=$HOME/.wispos-dev/known_hosts root@<ip>`.
  **Always pass that known-hosts file.** After a reflash the host key changes: `ssh-keygen -f ~/.wispos-dev/known_hosts -R <ip>`.
  A bare `ssh` falls back to `~/.ssh/known_hosts`, which has a stale entry for that address and refuses.
- sshd can lag the announcement by seconds at boot, and stops answering under memory thrash (banner timeouts). Use `ConnectTimeout=40`.
- BusyBox userland: no `join`, no `killall` by name that works reliably, `ps` columns differ, `ls --time` missing. `pkill -f` on the host
  kills your own shell (the pattern matches the command line); use `ps | awk` to pick PIDs.

### 2.2 Eyes and hands
- Screenshot: `XDG_RUNTIME_DIR=/var/run/0-runtime-dir WAYLAND_DISPLAY=wayland-1 grim -l 1 /storage/wispos/shots/NAME.png` then `scp` it.
  (Create `/storage/wispos/shots` after a flash.) Helper on the host: `/mnt/hdd/wispos-staging/wispos-os-20261007/tmp/pad.sh NAME "buttons" WAIT [HOLDms]`.
- Buttons: `/storage/wispos/dev/wisp-dev-pad start --clone "H700 Gamepad"` once per boot, then `wisp-dev-pad press down a`.
  Names: up down left right a b x y l r select start mode. It never types text. **The guide button (`mode`) needs a short hold (`--hold 40`)**:
  at the default 120 ms Steam treats it as a long press and shows the Power menu (Suspend/Turn Off/Restart/Sign Out). Back out with `b`.
- Steam UI is slow: wait ~5 s after each press before the screenshot, longer after opening pages. The first press after a screen change may
  only move focus. Library: guide (short) > down > a; the grid is alphabetical (B's are ~9 rows down; "BIT.TRIP RUNNER" sits right of "Runner 2").
  Game page: gear icon (4x right from Play) > Properties > Compatibility; "Show all compatibility tools" must be on to list Proton versions.
- Session helpers: `os/dev/steam-session.sh save|restore` keeps the Steam login token off-repo (`~/.wispos-dev/steam-session/`, 0600).

### 2.3 Safety net (do this before anything heavy)
- Start the watchdog: `/storage/wispos/dev/steam-watchdog.sh` (stops `wisp-steam` when MemAvailable < 90 MiB with swap free < 300 MiB, or
  memory PSI "full" avg10 > 75, three checks in a row). **It lives on the card and is wiped by a reflash.** Its log: `/storage/wispos/logs/watchdog.log`.
- **No swapfile on the SD card (operator decision 2026-10-08):** the dev 2 GiB `/storage/wispos/swapfile` was swapped off and deleted (it was unused; SD wear and speed); `dev/safety.sh` no longer re-enables it. zram is the only swap. Consequence: the dev watchdog's "swap free < 300 MiB" test is now always true, so it stops Steam whenever MemAvailable < 90 MiB for 6 s.
  (not persistent). It is a dev aid only; SD swap wears the card.
- Stop Steam cleanly with `systemctl stop wisp-steam` (it can show `failed` afterwards; `systemctl reset-failed wisp-steam` before `start`).
- Environment for logging is set with `systemctl set-environment PROTON_LOG=1 PROTON_LOG_DIR=/storage/wispos/logs/proton` (volatile). **[?]** it did not
  produce a Proton log; the container may filter it. Steam's own logs: `/storage/wispos/runtime/steam/logs/{console_log,compat_log,content_log}.txt`.

## 3. The game test (BIT.TRIP RUNNER, Steam app 63710)

3.1 The store lists it Windows-only (`linux: false`); it is in the operator's Family Sharing library; installs 61 MB. Directory: `steamapps/common/BIT.TRIP RUNNER`.

3.2 **Default tool = x86_64 Proton Experimental under the FEX compat tool [hw].** Steam on ARM64 auto-installed Proton Experimental
(`experimental-11.0-20261001-x86_64`), FEX-Emu, and Steam Linux Runtime 4.0 (x86). Launch chain from `console_log.txt`:
`reaper > FEX-Emu/fex-compat-tool > SteamLinuxRuntime_4/_v2-entry-point > Proton/proton > RUNNER.exe`; it ends in about 1 s. The tool's own log
`/tmp/fex-compat-tool-<pid>.log` says: `graphics_provider '/usr/share/guestos/fex-mesa/graphics_provider.json' didn't provide graphics_provider.json`.
That is an OS-provided x86_64 guest rootfs with Mesa (SteamOS ARM images ship it). WispOS does not. This path also downloads ~2.2 GB of x86
tooling we do not want. Also seen: Steam says "Grab a controller and kick back!" before the first launch (Steam Input does not recognise the
H700 Gamepad as a controller yet; matters for the SteamOS UI work).

3.3 **ARM64 Proton path [hw].** Steam's catalogue lists `Proton 11.0-2 (ARM64)` (app 4628740), requires `Steam Linux Runtime 4.0 - Arm64` (app 4185400,
dir `SteamLinuxRuntime_4-arm64`) and `fex-stable`. Selecting "Proton Stable" for the game installs them (needs ~2.3 GB download, 1.9 GB on disk, and
pushed memory pressure to 45 with the Steam UI running; the watchdog stopped Steam once, the download resumed cleanly). With it the launch passes
`reaper`, `srt-bwrap` (the runtime's container) and starts `wine`, `wineserver`, then `wineboot.exe --init`. **wineboot then runs for 15+ minutes**:
one thread, VmSize 50 MB, RSS 1.6 MB, **0 page faults, 0 I/O, 95% CPU of which 88% is system time**, ~900 involuntary context switches/s,
SigBlk shows SIGILL blocked (the thread is inside a SIGILL handler) with SigCgt including SIGILL. Interpretation **[?]**: Wine's native ARM64
code (built for ARMv8.2-A, `-mtune=cortex-x3` in Valve's `Makefile.in`) hits instructions the A53 lacks, Wine's handler catches SIGILL and the
operation is retried. Not proven: the kernel hides the PC of a running thread (`/proc/PID/stat` field 30 = 0), no strace/gdb/perf on the device.
Ways to prove it: (a) run the same `wine` binary under the host's qemu-aarch64 with `-cpu cortex-a53` and see SIGILL; (b) scan the ELF files
with `steam/lsescan.c` style tooling for LSE / RCpc / dot-product / fp16 opcodes; (c) bring a static `strace` for aarch64 into `/storage/wispos/dev`.
Also: the web UI (`steamwebhelper`) burned ~1.7 cores while only showing "Starting launch", starving the launch (see 5.1).

3.4 **ARMv8.0 overlay result [hw, 2026-10-08].** The overlay (`Azkali/proton-arm64-a57` release `11.0-1-beta5-v80`, asset `proton11-arm64-v80-a57.tar.zst`,
sha256 `96e987e65f9995c1e64423b8637c6a323c41e9fd4c4b9e0962b54d9881af58f4`, 86 MB, 837 entries; replaces `bin-arm64/{wine,wineserver,msidb}` and `lib/wine/*` including
`libarm64ecfex.dll`) was applied over Valve's `Proton 11.0 (ARM64)/files` (originals saved, see 2.4). With it **wineboot completes in ~2 minutes** (stock: spun for 15+ minutes
at 88% kernel time), the Wine services start (`services.exe`, `explorer.exe`, `rpcss.exe`, `svchost.exe`, `winedevice.exe`), and **the game process starts**. FEX logs
"Host CPU doesn't support atomics. Expect bad performance" and handles unaligned atomics itself. This supports, but does not prove, that stock Valve ARM64 Proton uses
instructions the A53 lacks (SIGILL loop in `wineboot`). A version mismatch (overlay 11.0-1-beta5 vs installed 11.0-2) did not prevent this.

3.4a **How to replay a launch by hand (what finally gave real errors) [hw].** Steam's logs hide the Proton output and `PROTON_LOG_DIR` must be a path the container mounts
(inside `compatdata/<appid>`, not `/storage/wispos/logs`). `SteamGameId` must be set or Proton writes no log at all. Capture the real environment with
`/storage/wispos/dev/capture-launch.py` (saves a `reaper SteamLaunch` process's cmdline+environ), then `/storage/wispos/dev/replay.py game` runs the same command with
`PROTON_LOG=1`, `PROTON_LOG_DIR`, `SteamGameId`, a chosen `WINEDEBUG` (`REPLAY_WINEDEBUG`), extra env (`REPLAY_ENV="A=1 B=2"`), a tag for the output file (`REPLAY_TAG`) and a timeout.
**The working directory must be the game's install dir** (`STEAM_COMPAT_INSTALL_PATH`), as Steam does: started in Steam's root, Wine maps the cwd to `S:\` and BIT.TRIP RUNNER
walked all of `S:\appcache\librarycache\*` and died with "string: failed to copy string: dst too small (32 < 40)" on a 40-char SHA-1 folder name (the message text is inside RUNNER.exe).
That wrong-cwd mistake invalidated my first DXVK-vs-WineD3D comparison; the results below were re-done with the right cwd. Helpers: `kill-game.sh` (never `pkill -f`/inline
patterns over ssh: the remote shell kills itself), `watch-game.sh`, `last-calls.py`, `sample-wine.py`, `find-string.py`.

3.4b **MILESTONE: BIT.TRIP RUNNER runs on the handheld [hw, 2026-10-08 03:31].** Title screen ("PRESS ANY BUTTON") rendered by a 32-bit Windows game through ARM64 Proton (Valve 11.0-2 +
the ARMv8.0 overlay) with FEX (wow64) on the Cortex-A53, via Wine's OpenGL path to Mesa 26.2.2 Panfrost (OpenGL 3.1, GLSL 1.40, Mali-G31 MC1, 244 MB "video memory"). Running it: ~1.5 cores
for the game (`RUNNER.exe` 13.4 GB VIRT, ~120 MB RSS), system MemAvailable ~175-240 MB, CPU 55 C on external power, UI processes still ~1 more core. Frame rate NOT measured yet.
Input did not reach the game from the virtual pad (title did not advance with a 120 ms or a 700 ms press); the real pad has not been tried; see 6.

The root-cause chain that had to be peeled, in the order met (each one hid the next):
  1. **Valve's stock ARM64 Proton spins in `wineboot --init` on the A53** (probable SIGILL loop; ARMv8.2 build). Fixed by the community ARMv8.0 overlay (3.4).
  2. **Steam's default tool is x86_64 Proton under FEX**, which needs an OS-provided x86 rootfs `/usr/share/guestos/fex-mesa` (3.2). Use "Proton Stable" (= Proton 11.0-2 ARM64) per game or globally.
  3. **No Vulkan for the emulated game**: DXVK fails `Failed to create Vulkan instance`, the game aborts with exit code 3. Use `PROTON_USE_WINED3D=1` (OpenGL).
  4. **The game's D3DX9 effect compiler is a stub in Wine**: `fixme:d3dx: ID3DXEffectCompiler ... CompileShader ... "vs_3_0" stub!` -> the game's own dialog "shader: failed to compile vertex shader".
     The game's install script is supposed to install DirectX 9 (`Dependencies\dxwebsetup.exe /Q`), but **dxwebsetup cannot work under Wine** (it crashes: `inseng` stub -> EIP 0). Fix: the **offline**
     DirectX June 2010 redistributable (`directx_Jun2010_redist.exe`, sha256 `053f76dc...c73b`): extract `Jun2010_d3dx9_43_x86.cab` -> `d3dx9_43.dll` (1,998,168 B, sha256 `0b28546b...4f5f`) into the prefix's `syswow64`.
  5. With real d3dx9_43: `shader: failed to create effect compiler ... error.aeshader E5033: Unknown target profile '__fx_2_0__'` -> also needs the native `D3DCompiler_43.dll`
     (`Jun2010_D3DCompiler_43_x86.cab`, 2,106,216 B, sha256 `2f23182e...8a1c`) into `syswow64`. Then run with `WINEDLLOVERRIDES=d3dx9_43,d3dcompiler_43=n,b`.
  Side lesson (cost two hours): my first replays ran the game with the working directory at Steam's root, so Wine mapped it to `S:\` and the game walked all of `appcache/librarycache` and died on a 40-char hash folder
  name ("dst too small (32 < 40)"). Always start a game in its install dir (3.4a).

Sustainable fix to build (not done): a small WispOS helper that, per prefix, installs the offline d3dx9/d3dcompiler (and vcredist) payloads from a pinned, hash-checked cache and writes the DLL overrides, run before first
launch; plus Steam default tool = Proton Stable ARM64 and `PROTON_USE_WINED3D=1` as the default for D3D9/D11 games until a Vulkan path exists. Keep the redistributable cache out of the repo (Microsoft payloads) and out of release images (download on first use).

3.5 **A custom tool inside Steam's `compatibilitytools.d` made the Steam UI hang [hw].** With the 1.9 GB standalone tool registered the web UI main
thread sat at ~100% CPU for 19+ minutes and no window ever appeared; with the folder moved away the window appeared in ~1 minute; with only a
manifest-only registration (`install_path` pointing outside) it still hung. The tool's `toolmanifest.vdf` requires app 4185400 (the ARM64 runtime), which was
not installed then; Steam never logged it. **[?]** whether installing the dependency first makes registration safe; not retested. Rule until proven:
do not drop custom tools into `compatibilitytools.d` on this device; use Steam's own tool downloads plus overlays on top.

## 4. Other findings from this session [hw unless noted]

- **Memory is the central constraint.** Steam UI + a 2 GB download + staging pushed `MemAvailable` to ~50 MB with the 768 MiB zram full; sshd then
  stopped answering (banner timeouts) while ping worked. Stopping Steam recovered to 770 MB at once. Steam's own steady state (signed in, idle) used roughly 0.5-0.7 GB (whole system 'used' column) across `steam` + 5-8 `steamwebhelper` processes; a per-process breakdown (PSS) has not been taken yet. This is the same signature as the earlier lock-up.
- **Cold Steam UI start is slow and variable**: 2-4 minutes normally, and it does not draw a window until the web UI finishes JS startup (code caches
  are rebuilt after every Steam self-update). Steam self-updated twice on the device within hours (seed 1790904859 > 1791249696 at first run > 1791415817 a few hours later); each update invalidates those caches.
- **sway crashed once on the first start after a flash** (status 139): `sway.service` starts before ROCKNIX's `111-sway-init` writes the sway config and
  no default exists. Fixed in source (default config staged); the card in the device predates the fix. First boot order still races.
- **`wisp-steam` was skipped at first boot** (ordered after `wisp-setup` while it was failing/restarting; systemd does not retry). Fixed in source:
  `wisp-setup` starts it itself on success.
- **The D-pad moved two rows per press** in `wisp-setup` because both the controller and the raw joystick event of the same device were handled. Fixed.
- **Resize bug:** STORAGE (32 MiB) could only grow ~25 GiB (3 reserved GDT blocks); a 58 GB card corrupted on the first-boot grow. Fixed (`-E resize=536870912`).
- **Steam's manifest URL is mutable** (always the current release), so pinning its hash is wrong; component URLs are content-addressed. The installer ignores the manifest.
- After Steam self-updated, `steamui.so` needed `libva` and the client needed `libvdpau`, `libssh2`, `libbrotli*`, `libasyncns` besides `libibus`; all six are baked
  in the image (`stage_rootfs.STEAM_LIB_PACKAGES`). A host-side scan of the older seed missed them; **the only reliable scan is on the device against the updated client.**
- The tool `Steam Linux Runtime 4.0 - Arm64` is `ownersonly`; Steam's catalogue (parse `appcache/appinfo.vdf` for the ids) lists the ARM64 tools. Valve's
  public app list needs an API key now; SteamDB blocks bots.
- A stray `https://dpaste.com/...` line appeared once in a command result where device output belonged. Ignored; never fetched.

## 4c. 2026-10-08 morning: why the handheld dropped off Wi-Fi after the reboot [hw]

Not a hang and not a MAC clash. From the boot report on the card (`last-boot.txt`, copied to `card-logs-20261008/`): `wlan0` associates at
13.9 s, then at 18.5 s `deauthenticating ... by local choice (DEAUTH_LEAVING)`, NetworkManager logs `Activation: failed`, and the report ends
with `phy0 Soft blocked: yes`, `wlan0 unavailable`. Cause: ROCKNIX `usr/lib/autostart/common/080-network` runs `wifictl disable` when
`wifi.enabled=0` (the shipped default); `/storage/.cache/rfkill/<wlan>` then stores `1` and is restored on the next boot. It was masked
while the first-run screen ran (it re-enables the radio); with Steam installed, `wisp-setup` exits at once ("already installed").
Hit every boot, so it would hit every user after their first reboot. Fixed in source (`os/rootfs/usr/lib/autostart/common/080-network`,
a WispOS override that only runs `rfkill unblock wifi`; test `test_wifi_is_never_switched_off_at_boot`); **not yet in an image**.

**Second cause, found when editing the card did not help:** `/usr/lib/autostart/common/001-setup` runs `chksysconfig verify` on every boot,
and that does `rsync -a /usr/config/ /storage/.config` whenever `/storage/.config/retroarch/retroarch.cfg` is missing. WispOS has no
RetroArch, so the condition is always true and **every boot overwrites `/storage/.config` (including `system.cfg`) with the image defaults**.
Editing `wifi.enabled` on the card therefore cannot stick (it was back to 0 after one boot; the saved rfkill file likewise). Consequences to
remember: no setting stored in `/storage/.config/system/configs/system.cfg` survives a boot; and the rsync is boot-time churn on the SD card
(see section 5). Settings that must persist belong under `/storage/wispos` or in our own files, not in ROCKNIX's `system.cfg`.

**What recovered this card (stopgap, dev only, outside any image):** from the reader PC, `/storage/.config/autostart/010-wifi-on`
(mode 755, content `rfkill unblock wifi`). `/usr/bin/autostart` runs everything in that directory after the common scripts and after `wait`,
and nothing in `/usr/config` overwrites it. Saved rfkill state `/storage/.cache/rfkill/platform-4021000.mmc:wlan` set to `0`.
Confirmed on hardware: after that the device stayed on Wi-Fi past 18 s and SSH worked. Remove the stopgap once an image with the fix is flashed.

Side finding: the Deco showed one private MAC under two names (`fedora`, `H700`) at 192.0.2.110; that address belonged to another
device and the handheld came back at .113. Look the device up by its announce (`~/.wispos-dev/devices.json`), not by a remembered IP.

## 4d. 2026-10-08: the black screen and the stalled Steam UI start [hw] (FIXED in source: `fresh_xwayland`)

**Cause (measured, not just argued):** Steam's UI window failed to appear (mode 1: window 1280x800 mapped in Xwayland, no sway view, panel black) or the UI spent minutes
in a synchronous React render (mode 2: renderer main thread at 100% user CPU, `OnFocusInternal`/`OnBlurInternal` and React `workLoopSync` on the stack, page on `routes/login`)
whenever Steam started on the **previous Steam's leftover Xwayland**, i.e. within ~10 s of the previous one (Xwayland exits on its own after ~10 s without clients).
Evidence: same 4 s stop-to-start gap, no other change: stock launcher 16/32, 20/40 and 4/8 starts bad (three series); Xwayland killed before the start: 7/8 fine; start delayed 13-25 s (so
Xwayland had exited): 23/24 fine, also when the SoC was kept hot (8/8 at 72-74 C, so not heat) and under the `performance` governor (7/8; `ondemand` 8/8, so not CPU speed);
**patched launcher (`fresh_xwayland` before each start): 16/16 fine.** That also explains why yesterday evening was fine (restarts were minutes apart; the first boot of a flash started
Steam on a clean Xwayland) and why this morning was not (a reboot starts sway/Xwayland, setup runs, Steam starts within seconds; I then restarted Steam back to back many times).
I overclaimed twice on the way (the `-cef-disable-gpu-compositing` flag after 2 successes, reverted; then "0 black of 19" counted too early): the series below are what to trust.

### Playbook: debugging a game that Steam launches wrongly (learned 2026-10-09; use this first, do not re-derive)
1. Search the web first (rule 6 in AGENTS.md / ~/.claude/CLAUDE.md). For this class of bug it found only general pointers (log location, pressure-vessel threads); the cause came from the device.
2. Read Steam's side: `logs/gameprocess_log.txt` ("adding PID", "no longer tracking PID N, exit code X"), `logs/compat_log.txt`, `/storage/wispos/logs/session/steam.log` (stderr of Steam and its children), and `journalctl` for the same second (a `coredump: <pid>(sh)` line means the launch shell was killed by a signal). Exit -1 within a second = a child killed by a signal; exit 0 with no window = the pressure-vessel container's command died (set `PRESSURE_VESSEL_VERBOSE=1 PRESSURE_VESSEL_LOG_INFO=1` and look for "Command killed by signal").
3. Capture Steam's real environment: set the game's launch option to `<script in the game's compatdata dir> %command%` (Steam stopped while editing `userdata/*/config/localconfig.vdf`; BusyBox: no `fold`, `ps -o` limited), the script writes `pwd`, `argv:`, `--- env` (`env | sort`), `--- fds` and `exec "$@"`. Then replay it by hand with `os/dev/diag/replay_exact.py DUMP SECS K=V...` and bisect one variable at a time (about 45-75 s per run, no UI needed). Remove the launch option afterwards.
4. Drive the UI with the dev pad (`wisp-dev-pad press a`): after a Steam restart the home screen needs about 3 minutes before it accepts input; first A opens the game page, second A is Play. Wake the screen before `grim` (`wisp-screen wake`, then wait 2-3 s) or the capture fails/blank. Zombie `WA.exe` leaders leave ghost fullscreen windows that cover the UI: judge a launch by a LIVE (non-`Z<`) process, not by sway windows.
5. **Do not let a dev guard kill a healthy run.** `os/dev/diag/mem-guard.sh` v1 stopped Steam when MemAvailable was under 90 MB alone; it fired at 66 MB during a normal install-script pass (15:30 UTC) and Steam printed `installscript_posix.cpp (525) Assertion Failed: Standalone evaluator returned error code` as it was killed (the same assertion appears whenever Steam is stopped mid-launch; it is a symptom of the kill, not a bug of its own). v2 needs MemAvailable < 90 MB AND free swap < 300 MB. Check `/storage/wispos/logs/mem-guard.log` whenever a test ends mysteriously with `wisp-steam` inactive.
6. **An odd screen after any idle period is Steam's SCREENSAVER until a button press says otherwise (2026-10-10; cost me ~10 steps and the operator's patience).** What it looks like in `grim`: a small cropped image carousel (art of library games cycling: Overwatch, Quake, Diablo IV ...) in the top-left ~418x250 px of the 720x480 panel, the account name with "Away" under it at the top of that region, everything else black. Sway then reports a normal fullscreen 360x240 Steam window (scale 2), `xrandr` is normal and the console log is quiet, so the logs and geometry say "healthy" while the picture says "broken". `wisp-screen wake` (the panel backlight/idle script) does NOT dismiss it; one pad press does (`wisp-dev-pad start --clone "H700 Gamepad"`, `wisp-dev-pad press b`: B is harmless on the home screen). **Rule: on any partial, dim, black or rotating-art screenshot, the FIRST action is one pad press and a new screenshot; look at logs, sway or xrandr only if the screen is still wrong after that.** Timed waits (an install, a Steam restart, a quiet download) are exactly when the screensaver starts, so a wait longer than a few minutes ends in one. Open: the appliance has no operator-set screensaver policy; decide whether a game-free idle Steam should show it at all (operator's call).
7. Dead ends (each cost minutes; do not retry): hiding or renaming a Steam-owned file (Steam re-extracts its whole client package); `EnableGameOverlay=0` in localconfig (the overlay is still preloaded); `-silent -no-browser` (web helpers start anyway); `systemd-run -p MemoryMax` (this kernel has cgroup v1 only); `PROTON_ENABLE_WAYLAND=1` (this Proton ships only the X11 driver); `user_settings.py` in the Proton dir (no log appeared; use the environment override in the replay); a shim `librt.so.1` on `LD_LIBRARY_PATH` or in `steamrtarm64` (works on the host, loses to the container's own library path); `GALLIUM_HUD_DUMP_DIR` files (another GL context overwrites them; read the on-screen HUD labels).

### SIGILL fallback overhead: measured (2026-10-09 17:00-17:12 UTC) [hw] (operator: "are the emulated armv8_2 to armv8_0 mappings causing a non-insignificant overhead?")
- **Cost per emulated LSE atomic: about 6 us** (`os/dev/diag/lse-bench.c`, 200,000 `ldaddal` through the fallback: 5.8-6.4 us each; the same atomic as an `ldaxr/stlxr` loop: 13-14 ns each, about 430x less). Our handler's own part is only about 190 ns (statistics build: 914,089 counter ticks at 24 MHz for 200,000 events), about 3%; the rest is the kernel's signal delivery and sigreturn. **So making the emulation arithmetic cheaper, or approximating it, cannot help** (and a non-atomic stand-in would risk corrupting refcounts); the only large saving is not trapping at all.
- **How often it fires** (statistics build `-DWISPOS_LSE_STATS`, test only; dump files per pid; the Steam session ran with it as `LD_PRELOAD`): 7.4 million faults by the time the UI was up (3.4 min after start, about 44 CPU-seconds of trapping), then **about 11,000 faults/s with the UI idle and about 16,000/s while navigating** (about 7% and 10% of one core). Two processes cause almost all: the Steam client (7.5M events, one site `libtier0_s.so+0x1f7d8` = 59%, top 8 sites = 92% of 270 sites) and `steamwebhelper` (1.9M; two sites in the binary at `+0x236470` and `+0x23bfd4` about 678k each, plus `libSDL3.so.0+0x38d94..df0` and `libtier0_s.so+0x1f6bc..820`, top 8 = 92% of 148 sites). The game process itself (Worms, ARMv8.0 Wine build) was not measured (run stopped).
- **Plan (not started): back-patch hot sites.** On the first fault at a site, rewrite that instruction in place into a branch to a small LL/SC trampoline that does the same atomic (acquire/release bits kept: ordering never weakened) and returns, so each site traps once. **ROOT CAUSE FOUND (2026-10-10 02:10 UTC; the hang is a consequence, the trigger is a Mesa/panfrost write past the end of a buffer):** with Wine's `+seh` channel on (diagnostic launch option `WINEDEBUG=-all,+thread,+timestamp,+tid,+seh`, log in `/storage/wispos/logs/steam-217200.log`), 5.5 s after the Start click Wine logged `handle_syscall_fault code=c0000005 ... pc=0xffff861dd108 ... info[0]=1 info[1]=0000ffff7b86c000 x0=0000ffff7b86bf00 x2=0x180 ... lr=0xffff7c7d5704 ... returning to user mode ... ret=c0000005`. Resolved in the live process (`/proc/PID/maps`): `pc` is `libc.so.6` +0xad108 (a memcpy-class routine), `lr` is `libgallium-26.2.2.so` +0x105704, the destination `0xffff7b86bf00` lies inside a `/dev/dri/renderD128` mapping (a panfrost buffer object, `ffff7b814000-ffff7b86c000`, 0x58000 bytes) at offset 0x57f00 and the copy is 0x180 bytes, so it overruns the buffer by 0x80 bytes into unmapped memory (SIGSEGV on a write). The libgallium code at the call site is a row copy that computes strides and block sizes from several helper calls and multiplies width by bytes per block: the shape of a **texture upload** (glTexImage/glTexSubImage-class) into a mapped buffer sized differently from the layout it uses. Wine converts that SIGSEGV into an access violation returned to the caller, which skips Mesa's unlock: Mesa's `simple_mtx` stays locked (word = 2), and the same thread's next GL call blocks on the lock it already holds: **a self-deadlock**, which is exactly the futex value, the zero CPU progress and the spinning main thread (waiting for the command-stream thread). The two GPU page faults that appeared in some of the hangs (VA `0xA17A200` and `0xA18A200`, 0x10000 apart, same low bits, TRANSLATION_FAULT_3, READ) are the GPU reading the same malformed data: a second symptom of the same bad upload, not a separate cause. Audio is excluded (run with `winepulse/winealsa/wineoss` disabled: no audio threads at all, identical hang); `csmt` is excluded; Mesa's atomics are excluded (no LSE/RCpc in libgallium; the SIGILL fallback printed only one LDADDAL and one CASPAL128 emulation in the whole session).
**The exact call and the whole sequence (run with Wine `+opengl,+seh`, 2026-10-10 02:19-02:22 UTC; log `/storage/wispos/logs/steam-217200.log`, 420k lines):** `glBindBuffer(GL_PIXEL_UNPACK_BUFFER, 2)`, `glPixelStorei(UNPACK_ROW_LENGTH 720, UNPACK_IMAGE_HEIGHT 480)`, **`glTexSubImage2D(GL_TEXTURE_2D, level 0, x 0, y 0, 720 x 480, format 0x1903 GL_RED, type GL_UNSIGNED_BYTE, pixels = PBO offset 0)`** (0x54600 = 345600 = 720x480 bytes copied into the PBO just before) -> `handle_syscall_fault code=c0000005` -> `warn:opengl:glTexSubImage2D returned 0xc0000005` -> wined3d carries on: state changes, `glBindTexture 12/13`, **`glDrawArrays(GL_TRIANGLE_FAN, 0, 4)` is the last line of the log at the same millisecond**: the command-stream thread (tid 0x14c) is parked in Mesa's futex (value 2) and the game's main thread spins in `NtYieldExecution` for ever. The match scene had just been drawn once (a frame at ~47 fps was on screen) and the HUD froze at 14.74 fps / 491.6 ms, identical for 48 s. So all hangs are one failure: **an upload of a 720x480 8-bit texture from a pixel buffer faults inside Mesa while Mesa holds its lock; Wine returns the exception to the game, which continues; its next GL call deadlocks on the lock its own thread still holds.** 720x480 is this panel's native size (the game's 8-bit primary surface at scale 1); the fault is intermittent (the same upload runs every frame in the menus without failing), so the trigger is something about the buffer/texture state at the match start, not the size alone. ### Steam-launched Worms: ROOT CAUSE FOUND AND FIXED (2026-10-09 13:00-15:00 UTC) [hw] (supersedes the "open" entry above)
- **Cause:** Steam preloads its in-game overlay (`steamrtarm64/gameoverlayrenderer.so`, 726 KB, constructors contain `ldaddal swpal casal swpa caspal`) into the game's launch shell and, through pressure-vessel's `--ld-preloads`, into the container. Steam's own `LD_PRELOAD` for the game, read from an environment dump: `/usr/lib/wispos/libwispos-ldadd.so : steamrtarm64/gameoverlayrenderer.so : ~/.steam/bin32/gameoverlayrenderer.so : steamrtarm64/../steamrtarm64/gameoverlayrenderer.so` (our fallback FIRST). Libraries initialise in reverse preload order, so the overlay's constructors ran before our fallback had installed its SIGILL handler: `sh` crashed (kernel: `coredump: <pid>(sh): |/bin/false pipe failed`; `LD_PRELOAD=<overlay> /bin/sh -c true` exits 132), Steam reported "exit code -1"; inside the container pv-adverb logged "Command killed by signal 4 (Illegal instruction)" and Steam saw a silent exit 0 with no window. The same happened on the previous card with BIT.TRIP RUNNER: **no Steam-launched game ever started on this device**; my hand launches (my own launcher, Steam client's environment, no overlay) hid it.
- **Bisect (replaying Steam's exact environment, `os/dev/diag/replay_exact.py`, from a wrapper-launch-option dump):** `LD_PRELOAD=ours` alone or `overlay:ours` -> Proton starts (log 300+ lines); `overlay` alone or `ours:overlay` (Steam's order) -> dies. `PATH` and `LD_LIBRARY_PATH` (Steam sets it to just the game folder) are irrelevant. `EnableGameOverlay=0` in `localconfig.vdf` does NOT stop the preload. Hiding the overlay file makes Steam re-extract its whole client package (bad).
- **Fix:** Steam lists a fourth entry AFTER the overlay, `~/.steam/bin32/gameoverlayrenderer.so`, normally absent. `wisp-steam-session` now puts a COPY of the fallback there (a link would be deduplicated to the first position). It initialises before the overlay, in the launch shell and inside the container. Nothing of Steam's is modified. A shim `librt.so.1` (overlay's own dependency) worked on the host but not in the container (the container's library path wins), so it was dropped. Test: `test_games_launched_by_steam_get_the_fallback_ahead_of_the_overlay_in_every_process`.
- **Evidence:** with the copy in place, Steam's exact environment keeps Worms running (Proton log 365 lines, game window mapped); pressing Play with the pad in the Steam UI started the real game (Steam tracked 4+ processes, `WA.exe` live, 7 processes), then the game showed its own "unable to initialise graphics using the required video mode" dialog at the half-resolution screen and at native (a Worms display-mode question, separate from this bug: the prefix's windowed-mode tweak is not applied under Steam's launch; not yet understood).

### Two boot slots, and what the QEMU power-cut test found (2026-10-12) [host + qemu]
1. **My own rename plan was wrong.** The 2026-10-11 design renamed `KERNEL` to `KERNEL.old` and then `KERNEL.new` to `KERNEL` in the initramfs. Between the two renames the card has no `KERNEL`: a power cut there leaves U-Boot nothing to load, and the initramfs that was to finish the job is inside the missing file. The design text said "recoverable at any point"; it was not. Found while writing the apply step (no image shipped it). Replaced by two slots and a one-letter switch (docs/WISPOS-UPDATE-DESIGN.md "Amendment").
2. **U-Boot's behaviour, read and then run.** Read in the pinned source (`boot/pxe_utils.c`, `common/menu.c`): no `PROMPT`/`MENU`/`TIMEOUT` means the default label starts without a menu; a label whose kernel cannot be loaded is skipped (`boot_unattempted_labels`). Then run: `os/boot/build-uboot-qemu.sh` builds a `qemu_arm64` U-Boot from the SAME patched source tree as the handheld's (30 s; the host lacks gnutls headers, so `TOOLS_MKEFICAPSULE` is off), and a probe card booted under it showed: `DEFAULT a` loads `/KERNEL` (`wisp.slot=a` on the kernel's command line); `DEFAULT b` loads `/wispos/b/KERNEL` (a nested FAT path works); b's kernel missing -> "Skipping b for failure retrieving kernel" and slot a starts; b's kernel empty -> slot a starts; **and a kernel file that is not a Linux image (random bytes) -> slot a starts too** (booti refuses it and U-Boot goes on to the next label); flipping the letter with a one-byte write in the FAT image is followed. Caveat: the H700 build boots through the `sysboot` command and this one through `bootmeth_extlinux`; both end in `pxe_process()`, the code under test, but the H700 itself has not run it.
3. **The QEMU end-to-end test (`os/qemu-update-test.sh`, `os/boot/qemu_update_test.py`)**: six QEMU machines in parallel (real initramfs, real busybox, real vfat driver, real `wisp-update`, the U-Boot above as the machine's firmware; a read-only FAT32 reader of its own looks at the "media" after every power cut and a stand-in for U-Boot PREDICTS the slot, checked against the slot the kernel reports on every boot). Scenarios: a real-size update (213 MB into slot b, restart, slot b boots from `/flash/wispos/b/SYSTEM`, the start is counted, confirm, restart without a trial); a payload whose system cannot be mounted (three starts, then the initramfs goes back, `FAILED-<id>`, the build is not offered again, cannot be applied by name); a kernel that is not an image (U-Boot falls back by itself, the stale marker is removed); power cuts (SIGKILL) after each commit step. **Bugs the cuts found, both in my helper, both invisible to the unit tests:** (a) a NEW directory's entry lives in its PARENT, so fsync of the files and of the directory itself did not persist it: a cut after the staging lost the whole `wispos/b` directory (and `wispos/update`, with the trial marker); `ensure_dir` now syncs every directory up to the card root. (b) On FAT the renamed file's size and first cluster are not in its new directory entry until the file's inode is written: a cut right after `rename` left `KERNEL`, `SYSTEM` and `PENDING` as empty files although the data was whole (the in-place letter flip, for which the empty marker would have meant "on trial with no guard", was protected only because the marker is read as unreadable and left alone); `durable_rename` fsyncs the file under its new name and then the directory. Both have in-process regression tests (events recorded in order) and mutants.
4. **Harness lessons.** A SYSTEM built before the helper changed made the first runs meaningless (the card in the test is built from `out/SYSTEM`: rebuild the rootfs first). The initramfs's busybox cannot run most applets under qemu-user (the shell re-executes `/proc/self/exe`, which is qemu there): the boot-step tests give it wrappers that run the real busybox applet. `os/fatwrite.py` refused directories more than one level deep (slot b is three); it now nests, byte-identical for one-level trees. The QEMU kernel builds in 83 s once the real kernel is built; the real kernel takes 7 min with the new initramfs.
5. **Not covered, stated plainly:** a new KERNEL that loads and then dies before its initramfs (recovery: change the letter on any PC; printed in `wispos/README.txt`); the SD card's own behaviour on a power cut (sector atomicity is assumed, as for every FAT update); the Restart button's exact helper name in Steam; U-Boot on the H700 itself.
