# WispOS as a single-purpose OS: design and plan

Recorded 2026-10-07. Operator intent: a very light "bazzite for the RG34XXSP": boots
into Steam Big Picture ("GameMode UI"), can switch to a lightweight gamepad-friendly
desktop and back, supports all the device's hardware, can add non-Steam games, and
ships with SSH, the `wisp` user and `vi`. This document records what the evidence
supports, the decisions taken, the open unknowns, and the build phases. Nothing here
has run on the handheld yet (it was unreachable when this was written); every claim
below is labelled as measured, documented, or untested.

## Principle: WispOS is its own OS, built from ROCKNIX's open recipes

Revised 2026-10-07 at the operator's direction: no overlay, no fallback to the ROCKNIX
frontend. ROCKNIX is open source and its H700 boot chain is fully described by recipes
(U-Boot with its DRAM and PMIC patches and defconfig, Arm Trusted Firmware, the kernel
configuration and device trees, the initramfs). WispOS builds each stage from source with
those recipes and replaces everything above them with its own userland. The earlier failed
boot-chain attempts improvised instead of following these recipes; following them is the
method. Each stage is verified before the next is built on it:

1. **Bootloader**: U-Boot v2026.01 + BL31 built from ROCKNIX's recipe. **Done**:
   `os/boot/build-uboot.sh`, hash-pinned sources, reproducible, structurally equal to the
   bootloader on the handheld (not yet booted).
2. **Kernel + initramfs + device trees**: from ROCKNIX's `linux.aarch64.conf`, patches and
   `dts`. Next.
3. **Root filesystem**: WispOS's own (`os/rootfs/` baked in), starting from the same
   userland binaries ROCKNIX uses (no apt on this host) pruned to what the single purpose needs.
4. **Image**: assembled and written to the card; booted on the handheld.

A full from-source rebuild of every ROCKNIX userland package would need its Docker/apt build
environment, which `HOST-SAFETY.md` forbids on this host without explicit per-operation approval,
so userland pieces are fetched as hash-pinned binaries or built with the host's existing cross tools.

## Memory and robustness (lessons from 2026-10-06)

- Stripping the ROCKNIX frontend and extras freed about 100 MB (measured); Steam itself
  stays about 700-790 MB, and the tried Steam switches did not reduce it.
- Hard-killed Steam leaves `/dev/shm/u0-Shm_*` files (about 26 MB each, 355 MB seen):
  the session unit clears them at start (`wisp-shm-clean`, in the rootfs).
- An overload froze the device (kernel up, userspace starved). A single-purpose device
  needs an out-of-memory guard: `systemd-oomd` is present in the image; wire it to
  cgroup slices (`steam-ui.slice` protected/pressured, `game.slice`), as the whitepaper
  proposes. Not enabled in v0 because it was not tested.
- zram: 768 MiB lz4 now. The sizing test was not completed; do not change it without
  the safe test procedure in `OVERNIGHT-REPORT-20261006.md`.

## Build structure

`os/boot/` builds the bootloader; `os/rootfs/` holds files baked into the root filesystem;
later `os/` gains the kernel and image builders. All work trees and outputs live under
`/mnt/hdd/wispos-staging/`; every input is hash-pinned; builds must be reproducible.

## Risks and open decisions

1. **Session user.** The session runs as root for now, as in every working run; moving Steam and Sway to `wisp` needs seat, device-node and runtime-directory permissions worked out (phase 2). `wisp` is a member of `wheel`, `video`, `audio`, `input`, `render`, `netdev` and `users` already.
2. **Default password.** `wisp`/`wisp` on an always-on SSH is publicly guessable; this is the operator's explicit choice. Root has no password login (key only).
3. **GameMode ambition.** If real gamescope is a hard requirement, phase 4 gates the whole
   plan on PanVK working acceptably on a single G31 core; that may not be achievable.
4. **Steam updates.** Updates changed binaries and dependencies once already (missing
   `libva`). A compatibility gate (dependency check, instruction-coverage scan, emulator
   tests, SSH sign-in smoke test) should run before any new client version is adopted;
   pinning with `steam.cfg` is an option, untested here.
5. **Untested.** Nothing built here has run on the handheld yet.

## Steam UI integration targets (operator, 2026-10-07)

If the Steam UI runs well, WispOS should let it own the device-level settings instead of shipping its own
tools: Wi-Fi management, volume (mapped to the hardware volume keys), the "M" button as the Steam button
and, held, as a modifier, and formatting a card in the second TF slot. Status of each, from what is known:

| Want | What the evidence says | Unknown / to verify on the device |
| --- | --- | --- |
| Wi-Fi in the Steam UI | Steam's client links `libnm` (it is in `native-libs.lock.json`); the image runs NetworkManager with the iwd backend, which is what such a page talks to | Whether Steam's network page works on this stack; `wispos/wifi.conf` stays only as a first-connection fallback and for headless setups |
| Volume keys | The device tree has a `gpio-keys-volume` node (KEY_VOLUMEUP, 0x73, and a down key); audio is PipeWire with the pulse layer, which Steam's volume control uses | Who consumes the key events (ROCKNIX's input service, sway bindings, or Steam Input) and that the slider and keys stay in sync |
| "M" button = Steam menu, held = modifier | The joypad node `GPIO BTN_F` emits code 0x13c, which is `BTN_MODE`, the code Steam Input treats as the Guide/Steam button | Which physical key that is (check with `evtest`); the hold-as-modifier needs a Steam Input layout or a small daemon; SDL mapping lives in ROCKNIX's `mkcontroller`/controller database |
| Format the TF2 card from the UI | The device tree enables the second SD controller (`mmc@4022000`, with a card-detect GPIO and its own supply). Steam's binaries reference `/usr/bin/steamos-polkit-helpers/*` and the SteamOS manager, which is where SteamOS implements formatting | Kernel enumeration of a card there (needs the device); the helper must be written by us, must act only on the TF2 block device, and must refuse the boot card, and a library folder needs auto-mounting |

All of these depend on Steam's UI actually running on this display and input stack, which has not been shown on
this image yet. They are also independent of gamescope: they are D-Bus services and helper programs, not
compositor features, though Steam may gate some of them on detecting SteamOS (to be found empirically).

### Desktop mode: direction and proposed stack (operator's wishes 2026-10-12; a PROPOSAL, nothing built, decisions open)
**The wishes:** "something very light, but full featured, maybe some WM and a dock", and a desktop with "smart cursor navigation that could be used for the gamepad too".
**What the image already has** (read from the built SYSTEM, 2026-10-12): sway 1.x on wlroots 0.19 (resident for Game mode, so desktop mode adds no second compositor), `swaybar`, `foot` terminal (464 KB), `bemenu` (68 KB), `wvkbd-mobintl` on-screen keyboard (694 KB), `swayimg`, `grim`, `wlr-randr`, `nmcli`/`iwctl`/`bluetoothctl`. Sway uses `wlr_foreign_toplevel_handle_v1` (a dock can list, focus and close windows), `wlr_layer_shell_v1` (a dock can reserve an edge), `wlr_virtual_pointer_manager_v1` and the virtual-keyboard and input-method protocols come with wlroots. The kernel has `INPUT_UINPUT=y`, `INPUT_JOYDEV=y`, `INPUT_EVDEV=y` and USB HID, storage, UAS and (as modules) RTL8152/USBNET, so a pad daemon, a USB keyboard, a disk and a USB Ethernet adapter all work once the port is in host mode.
**"Smart cursor navigation" is three different things; the proposal builds the first two and defers the third:**
1. *Focus navigation (D-pad).* D-pad = arrow keys and Tab, A = Enter, B = Escape. Works in every toolkit application and in our own shell with no extra software; the dock, launcher and settings are ours, so every widget is focusable by construction. The browser has its own: WPE WebKit has the `enable-spatial-navigation` setting (arrows move between focusable elements, since 2.4) and Chromium the `--enable-spatial-navigation` flag; whether Cog turns it on for a D-pad press is not documented and has to be tried.
2. *A plain pointer (right stick, triggers)* for what does not take focus navigation. The Steam Deck's desktop layout is the convention (right pad = mouse, R2 = left click, L2 = right click, left pad = scroll; A = Enter, B = Esc from a community post, not Valve documentation). Steam is OFF in desktop mode, so Steam Input is not there to supply it: a small daemon of ours (uinput or the virtual-pointer protocol) would, which is an **exception to the "controller mapping is Steam Input" ruling that needs the operator's yes**; copying the Deck layout keeps it the same convention.
3. *Content-aware snapping* (the cursor jumps to the nearest clickable thing in any application). Wayland compositors do not know what is inside a window; it needs the accessibility tree (AT-SPI), published only by applications that opt in (GTK/Qt, browsers with accessibility on, which costs memory). Web search 2026-10-12 found no gamepad project that does this on Wayland; closest are wl-kbptr (a letter grid and bisection driven from the keyboard, needs layer-shell and virtual-pointer, so it runs on sway) and `hints` (an AT-SPI overlay). Deferred past 0.1.0; measure its cost first.
**Proposed shell:** sway stays the window manager (tabbed/maximised layout by default on a 720x480 panel, floating for dialogs); one small shell of our own for dock, launcher and settings, drawn with the UI-language tokens (`os/ui/wisp-ui.h`; a dock is a new component, so it is added to `docs/WISPOS-UI-LANGUAGE.md` first), as a layer-shell client with the foreign-toplevel protocol for the window list. The dock is also where the SSH and USB toggles live (`wisp-ssh`, `wisp-usb`), plus Wi-Fi, Bluetooth, volume and brightness. The gamepad daemon, `wvkbd` for text entry, `foot` as the terminal.
**Weight:** with Steam off a 1 GiB device has roughly 600-700 MB for the desktop. Everything above costs tens of MB; the browser is the one heavy piece and no published figures exist for Cog/WPE, Epiphany or Firefox on a 1 GiB Panfrost board (searched 2026-10-11). Cog is a launcher without tabs or an address bar, so "full featured" browsing is a measurement and a choice: Cog/WPE with our own chrome, Firefox, or Chromium, measured on the device (resident memory, start time, three real pages, video).

#### The dock and the application menu (operator's requirements 2026-10-12 "if we write our own dock"; the design is LOCKED, nothing built)
**Requirements (operator):** icons; adding and removing items; a way to open the full menu of applications; tracking of open windows. Implied by the roadmap: a way back to Game mode; usable from the gamepad alone.
- **What it is.** One program, `wisp-dock` (C; wayland-client, wlr-layer-shell, wlr-foreign-toplevel-management; software drawing with pixman and fcft; PNG with libpng; Liberation Sans and the tokens of `os/ui/wisp-ui.h`, so it is the same design language as the setup screen). It draws the dock strip and, on demand, the full-screen application menu as an overlay. Everything it links is already in the image (libwayland-client, libpixman, libfcft, libpng16, libfreetype); only headers are needed at build time, pinned and hash-checked the way the setup screen pins SDL's, plus the two layer-shell and foreign-toplevel protocol XMLs run through the host's `wayland-scanner` (1.22). No SVG library is in the image, so icons are PNG.
- **Split for testing.** A pure model (desktop-entry parser, application list, pin store, window list, selection and focus state machine, layout and hit testing) is unit-tested natively on the host; a thin Wayland shell on top is tested in QEMU under a headless sway (software renderer) with `grim` screenshots against design PNGs (`os/dock/design/`), the way the setup screen is.
- **Applications and icons.** `.desktop` files from `/usr/share/applications` (ours; ROCKNIX's leftovers there, such as `cups`, `wine`, `htop` and `nvtop`, are not apps of this product and stay out) and `/storage/.local/share/applications` (the user's; later non-Steam games drop in here with no new interface). It honours `Name`, `Icon`, `Exec` (field codes dropped), `Terminal` (run in `foot`), `NoDisplay`, `Hidden`. `Icon` is an absolute path or a name looked up in `/usr/share/wispos/icons` (our own set, drawn in the UI language at 48 and 96 px), `/usr/share/icons/hicolor/<size>/apps` and `/usr/share/pixmaps`; no icon found = a letter tile in palette colours, never a blank.
- **The strip.** Along the bottom edge, 44 px high on the 720x480 panel, reserving its space so maximised windows are not covered. Left to right: the Applications button, the pinned items, then the other open windows; a running application has an accent dot under its icon; the Game mode item is always present (the way back); at the right the status icons (Wi-Fi, volume, battery, USB and SSH state) and the clock, which open a quick-settings panel holding the SSH and USB toggles. Event driven: no polling, the clock is a timer once a minute, the battery and Wi-Fi follow uevents or a slow timer.
- **Adding and removing.** Pins live in `/storage/.config/wispos/dock`, one desktop-file ID per line, in order. Pin from the application menu or from a running window's item; unpin, and move left or right, from the item. First run is seeded with the browser, terminal and settings. A change rewrites that few-bytes file; nothing is written otherwise (SD writes stay rare).
- **The application menu.** A full-screen grid of icon and name, flat and alphabetical, scrolled by the D-pad; A launches, X pins or unpins; text entry through the on-screen keyboard (or a USB keyboard) filters it. Memory only while open.
- **Open windows.** `wlr-foreign-toplevel-management`: title, app_id and state events, activate and close requests. A window is matched to its application by app_id (Xwayland windows use their X11 class) or `StartupWMClass`; for 0.1.0 one item per window, so an application with two windows shows two items.
- **Gamepad.** M (the Mode button, free in desktop mode) summons the dock: while summoned it asks for keyboard focus (layer-shell lets a surface request that), so the pad daemon's ordinary arrow, Enter and Escape keys drive it and no side channel is needed beyond the summon itself (a signal, like `wvkbd`'s). Proposed: D-pad moves, A activates, X pins or unpins, Y closes the window, B gives focus back; Start opens the application menu. Placement, size and these buttons are the operator's to change when he sees a first screenshot.
- **The pad daemon, `wisp-pad`.** Grabs the H700 pad (EVIOCGRAB) and presents a virtual mouse and keyboard through uinput. Started by the switch to desktop, stopped by the switch back (it releases the pad, so Steam Input sees the device untouched in Game mode). Layout from the Deck's desktop configuration: right stick = pointer with acceleration and a slow modifier, R2 = left click, L2 = right click, left stick = scroll, D-pad = arrows, A = Enter, B = Escape, X = on-screen keyboard, Y = Space (the A/B/X/Y mapping is from a community post, not Valve documentation: to be confirmed on a Deck or in Steam's own desktop configuration before it is final).

#### Controls and the on-screen keyboard in desktop mode (LOCKED 2026-10-12 with the operator's changes: the stick split and the shoulder buttons are his, the other rows were put to him as proposed and not changed; nothing built)
**What the pad has** (read from the device tree the RG34XX-SP builds on, `rocknix-singleadc-joypad`, 2026-10-12; not yet read from the running device): two analog sticks (ABS_X/Y and ABS_RX/RY through an ADC multiplexer, dead zone 128, fuzz and flat 32 in the driver) with stick clicks (BTN_THUMBL, BTN_THUMBR), a D-pad as four buttons, A/B/X/Y, L1/R1 and L2/R2 as digital buttons (the four shoulder buttons sit in one row, the L2/R2 pair on the inner side: operator, 2026-10-12), Select, Start, Mode, and the volume rocker as separate keys. If "cursor tab" meant the pointer itself jumping from one clickable thing to the next, that is the content-aware snapping parked until after 0.1.0 (it needs the accessibility tree); focus navigation gives most of it now, and the same stick would drive the snapping where it exists.

The dock is hidden while it is open and the window above it is re-tiled to the space left (a bottom layer-shell surface with its own exclusive zone).

#### Browsing with the gamepad (the operator's clarification 2026-10-12: he meant usability with the pad as the main input, not speed; and the browser's main job will be downloading things for the device, third-party games and AppImages; the browser layer ACCEPTED 2026-10-12 on the condition below; nothing built)
**Prior art, read and not recalled.** Valve's Steam Input templates are in the Steam client the project already downloads (`controller_base/`); `os/dev/diag/steam-bindings.py` prints them:
- *Deck desktop* (`desktop_neptune.vdf`): A Enter, B Escape, X show keyboard, Y Space; D-pad and the LEFT stick are arrow keys; the RIGHT stick is the mouse (its click is the left button); the triggers are the left and right mouse buttons; the bumpers are Ctrl and Alt; Menu is Tab. This is the operator's stick split. The Xbox desktop template has the same shape (A Enter, B Space, X and Y Page Up and Down).
- *Valve's Web Browser template* (`templates/controller_neptune_webbrowser.vdf`; a community report says Steam applies it by itself when it sees a browser): the LEFT stick is the scroll wheel, the right stick the mouse, the D-pad the arrows, **B is mouse Back and Y mouse Forward**, X the keyboard, A Enter and Space, the triggers the clicks, the bumpers Back and Forward, Menu Ctrl+W (close tab), the grips middle click and Ctrl. In Steam's own browser preset the D-pad moves focus, the left stick scrolls and the right stick is the mouse.
- *Other browsers* (web search, secondary sources): the PS4 browser has a left-stick cursor, Circle for Back and R3 for zoom; Xbox's Edge has a browsing mode and a "game controls" pass-through mode, B is Back; Fire TV's Silk offers spatial navigation and a cursor with a menu to switch, and Opera's TV developers report that spatial navigation on ordinary sites is likely to be frustrating (the focus seems to jump at random), that clickable divs are invisible to it, and that text entry is the weak spot.
**What that says.** (1) Valve does not use one layout for everything: a browser gets its own (Back on B, scroll on the left stick). (2) For the open web the robust base is pointer, scroll and keyboard; spatial focus is a bonus that works on well-formed pages, menus and lists. (3) Typing is the pain, so reduce it. (4) Every console browser has Back on a face button.
**Proposal: a browser layer.** `wisp-pad` switches layer on the focused window's app_id (sway reports it; Steam switches by program the same way) and the keyboard hint strip shows which layer is on. Unchanged from the locked layout: right stick pointer, R1/L1 clicks, L3 slow, R3 scroll toggle, L2/R2 Tab and Shift+Tab, A Enter, X keyboard, Start the application menu, M the dock. Changed inside a browser only: the **left stick scrolls** (smooth and proportional, Valve's choice) instead of sending arrows; the **D-pad moves the focus** (the operator's "cursor tab" navigation, on the D-pad here): in a text field and in every other program it sends the plain arrow keys, on a page it sends F13 to F16, which only our extension listens for and turns into spatial focus, so a real keyboard's arrows are never taken from it; **B is Back, held it is Escape; Y is Forward**; **Select opens a browser actions list** (Back, Forward, Reload or Stop, Address, Tabs, New tab, Close tab, Zoom, Reader view, Desktop or Mobile site, Downloads) that sends the browser's own shortcuts, so it works with any browser. The alternative that keeps the operator's original rows everywhere (left stick = focus, scroll on R3) loses Valve's proportional scroll; his call.
**Input parity: the operator's condition (2026-10-12).** "Gamepad-first, but the UX still has to make sense for keyboard and mouse; someone may prefer VNC." The rule, for the whole desktop shell and not only the browser: *gamepad-first, never gamepad-only*.
1. **Additive.** A pad behaviour exists only while the pad is the input. With no pad events nothing changes: a keyboard and a mouse, local or over VNC, get stock behaviour everywhere. The left stick sends the same hi-res wheel events a mouse wheel sends; B and Y send the mouse's Back and Forward buttons (what Valve's template does); L2 and R2 send Shift+Tab and Tab.
2. **Nothing is pad-only.** Every action of the shell and of the browser layer has a keyboard path and a pointer path (the table). A convenience that takes a key or a gesture away from a keyboard or a mouse is a defect.
3. **The extension never takes real keys.** Pad spatial moves arrive as F13 to F16 (no physical keyboard sends them; pages ignore them), not as arrows; plain arrows stay native for keyboards, text fields and every other program. A keyboard user who wants spatial focus gets an opt-in shortcut.
4. **The on-screen keyboard appears by itself only when the pad was the last thing touched** (within about ten seconds): never for someone typing on a keyboard or clicking with a mouse, never over VNC; showing and hiding it by hand is always possible.
5. **The pointer hides only while the pad drove the last input** (the pad daemon sets sway's `hide_cursor`, and clears it when the pointer stick or a mouse moves); a mouse user's pointer never vanishes.
6. **The browser keeps a compact, always visible single-row toolbar** (tabs and address bar, about 36 px), so the mouse and keyboard have the browser's own UI; the actions list is the pad's shortcut to the same commands, and F11 gives full-screen reading.
7. **Pointer states for every component** (not in the locked pictures, which show the pad's focus): hover is a tile filled with `WISP_UI_LINE`, a press the accent; right-click on an item is the item actions list, the wheel scrolls menus and lists; hints name the pad's buttons only while the pad is in use.
| Action | Gamepad | Keyboard (proposed; Super-based so browsers and terminals keep their keys) | Mouse |
| --- | --- | --- | --- |
| Application menu | Start | Super | click the Applications button |
| Summon the dock | M | Super+D | the dock is always visible |
| Switch windows | dock, A | Alt+Tab (the shell's switcher) | click the item in the dock |
| Item actions (pin, move, close) | Y | Menu key or Shift+F10 | right-click the item |
| Quick settings | A on the status group | Super+S | click the status group |
| On-screen keyboard | X | Super+K (a real keyboard needs none) | the toggle in the quick settings |
| Browser Back, Forward | B, Y | Alt+Left, Alt+Right | the mouse's side buttons, the toolbar |
| Scroll | left stick | wheel keys, Space, Page Up and Down, arrows | the wheel |
| Move between links | D-pad | Tab, Shift+Tab (L2 and R2 send them) | click |
| Actions of the focused window | Select | Super+A | the browser's own toolbar and menus |
| Downloads toast | A, B | Enter, Esc | click its buttons |
**The page itself:** one WebExtension for Firefox and Chrome, which acts only on the pad's own keys (F13 to F16) and so leaves keyboard and mouse behaviour alone: in-page spatial navigation (the WICG spatial-navigation polyfill, MIT licensed per its npm listing, to be confirmed in its repository, plus a rule that treats `cursor: pointer` and role or tabindex elements as targets and scrolls when nothing lies in that direction), a visible focus ring, last input wins between the focus ring and the pointer, a click assist that sends a near miss to the nearest link, and the keyboard opening by itself when a text field gets the focus (as an input method, so the keyboard can also show what is being typed).
**Size.** The panel is about 254 ppi, so at a device scale of 1 a 16 px page font is 1.6 mm. Run the browser at a scale of about 1.75: the page then sees about 410 CSS px, the phone layout, with large targets. Treat the handheld as a phone in landscape.
**Less typing.** A start page of our own (big tiles in the design language, a search field, recent sites); the browser's sync for bookmarks, history and passwords; later a phone as the keyboard.
**Downloads, the browser's main job here.** One landing folder (`/storage/downloads`; Firefox's `DefaultDownloadDirectory` policy). When a file completes (inotify, not the browser's own panel) the shell shows a toast with the actions that fit it: an AppImage becomes an application (made executable, its name and icon read, a `.desktop` file written under `/storage/.local/share/applications`, which the locked application menu already reads, so it appears there and can be pinned); an x86-64 AppImage or Linux binary needs the compatibility layer (FEX), an aarch64 one runs as it is; an archive is extracted to `/storage/games/<name>`; a Windows installer or executable gets "Add to Steam" (a non-Steam shortcut with the Proton compatibility tool, the mechanism of the FFXI pilot); anything else "Show in Downloads". Type-2 AppImages need FUSE: the image has libfuse 2 and `fusermount`, and `--appimage-extract-and-run` is the fallback. This is the handler for the file you just downloaded, not a file manager.
**Decided (operator, 2026-10-12):** the browser layer, on the condition in the next paragraph; the downloads handler is in 0.1.0 (its "Add to Steam" action depends on the non-Steam-shortcut mechanism of the FFXI pilot, which is not built; the AppImage and archive actions are self-contained). **Open:** the extension and the start page (the layer works without them: scroll, Back, Forward and the actions list are the shell's).

#### Software on the device: package managers, Flatpak, containers (operator question 2026-10-12; research only, nothing built)
**Short answer:** yes, but not a package manager for the OS itself. The system is a read-only signed squashfs replaced as a whole (docs/WISPOS-UPDATE-DESIGN.md), so `apt`, `pacman` or `rpm` on the host would have no package database to manage and an OS update would remove whatever they installed (SteamOS has the same constraint). What lives beside an image OS:
| Option | What it gives | What it costs here |
| --- | --- | --- |
| Flatpak (Flathub, user install under `/storage`) | sandboxed apps with their own runtimes, the usual app store of immutable gaming distros | flatpak, ostree, bubblewrap, xdg-dbus-proxy, appstream, libseccomp, libcap, libsoup and gpgme are NOT in the image. **The pinned ROCKNIX tree has recipes for all of it (Flatpak 1.18.0, ostree 2026.3) and Flatpak app addons for aarch64: Firefox, Chromium, Brave, Moonlight, RetroArch, MAME, ScummVM, SuperTuxKart, VacuumTube (Chrome and Steam Link are x86-64 only)**: precedent on our own base. No prebuilt addon is among the release assets, so we would build it from those recipes. Runtimes are hundreds of MB each, Flathub's aarch64 coverage is partial, and x86-64-only apps would need FEX inside the sandbox |
| A distro container: a Debian, Arch or Fedora arm64 rootfs in a chroot or bubblewrap with Wayland, audio and GPU passed through (Distrobox-like) | a real `apt`, `pacman` or `dnf` for whoever wants one, beside the OS and never touching it | a rootfs download (about 250 MB for a minimal Debian) and a launcher; the image has `chroot`, `unshare` and `nsenter` (BusyBox); GPU passthrough to be tried |
| AppImage | single files, no install step | libfuse 2 and `fusermount` are in the image; aarch64 AppImages are a subset; x86-64 ones run under FEX |
| Nix (a single-user store on `/storage`) | a very large aarch64 binary cache without touching the OS | GUI programs need GL wrappers off NixOS; not tried |
**The kernel is not the obstacle** (read from the build config): user, pid, net, uts and ipc namespaces, cgroups and memcg, seccomp, overlayfs, FUSE, squashfs with xz and zstd, binfmt_misc, ext4, btrfs, f2fs, exfat and ntfs3 are all on.
**Decided (operator, 2026-10-12): Flatpak happens after 0.1.0.** Recommendation, which he accepted: 0.1.0 gets nothing of this beyond the downloads handler above. After it, in this order: Flatpak (the mainstream answer, and the browser could then come from it), then an opt-in container for people who want apt or pacman; each with a gamepad-first front end in the design language (a store over Flathub's catalogue, not a desktop app store). What to keep in mind: the SD card fills with runtimes and games, and the appliance's job: Steam stays the primary place for games.

#### Web browsing in desktop mode: the performance side (research 2026-10-12; nothing built; the browser is NOT chosen)
**The constraints, as measured or read today.** 4 x Cortex-A53 (no JIT-friendly extras, no LSE), about 600-700 MB free with Steam off, a 720x480 panel, one Mali-G31 core on Mesa 26.2.2 Panfrost (GL 3.1, about 244 MB of shared "video memory"; sway and Steam's own Chromium UI already render through it), and the pad. **No hardware video decode:** `CONFIG_VIDEO_SUNXI_CEDRUS` is not set in our kernel and the 7.2 `cedrus.c` lists only the A64, H5 and H6; a mainline series "arm64: allwinner: h616: Support Video Engine" (July 2026, reusing the H6 variant, VP9 not included) is the way in but is not in our tree, and the image's ffmpeg has only the stateful `h264_v4l2m2m`/`hevc_v4l2m2m` decoders. For scale, Steam's UI (Chromium) takes about 1.7 cores at idle on this stack (notes 5.1): a Chromium-based browser starts from a hungry baseline.
**What the image has** (read from the built SYSTEM): glibc 2.41, GTK 3.24, NSS/NSPR, CUPS, ATK, ALSA, PulseAudio and PipeWire client libraries, GBM, EGL/GLES, GStreamer core (only `coreelements`, no video plugins), ffmpeg 7.1 libraries. **No browser, no mpv, no yt-dlp.** Official Firefox 157.0.1 needs, on arm64, glibc 2.28+, libstdc++ 6+, GTK 3.14+ and glib 2.42+ (Mozilla's system-requirements page, 2026-10-12): the image meets them. Google began offering official Chrome builds for Linux ARM64 (.deb/.rpm) in July 2026 (press reports; not announced by Google; the download page may still offer amd64 by default). Both are downloaded on first use like Steam, never shipped in the image.
**The levers, in the order I expect them to matter** (the order is judgement; none is measured on this board, and published numbers for similar A53 boards are thin: forum answers for a Pi Zero 2 W, the same CPU at 1 GHz with 512 MB, call modern browsing rough and tell people to use Chromium, without data):
1. *Block ads, trackers and third-party scripts.* Firefox can have uBlock Origin installed by policy: `distribution/policies.json` (or `/etc/firefox/policies`) with `"ExtensionSettings": {"uBlock0@raymondhill.net": {"installation_mode": "force_installed"}}` (`install_url` is optional for AMO add-ons from Firefox 153; firefox-admin-docs.mozilla.org). Chrome dropped Manifest V2, so the full uBlock Origin is no longer offered there; uBlock Origin Lite or a DNS/hosts blocklist replaces it (from general knowledge, to verify).
2. *The mobile site by default* (a mobile user agent and a layout width near 720 px), one press to ask for the desktop site: lighter pages, bigger targets.
3. *Memory discipline.* Few content processes, background tabs unloaded (`browser.tabs.unloadOnLowMemory` exists in Firefox, off by default, per a user report; Fission decides the process count and `dom.ipc.processCount` does not cap it: to verify on 157), small memory cache, **no disk cache and a long session-save interval** (the card must not be written constantly: operator rule), and a cgroup around the browser with `memory.max` and group OOM kill so a runaway tab kills the browser and never freezes the handheld (the lesson of the earlier overload test). A ceiling alone made Steam's UI thrash (notes, UI memory plan), so the browser's own unloading comes first and the hard limit is the safety net.
4. *Rendering.* 720x480 is only 0.35 megapixels, an advantage; compare GPU compositing against software for each browser (the Preferences policy can set `general.smoothScroll`; most other prefs go in the profile's `user.js`, because the policy only accepts a list of prefixes).
5. *A compact browser chrome:* one row for tabs and the address bar, nothing else, full-screen reading; every one of the 480 lines counts (Firefox `userChrome.css`).
6. *The pad:* the pointer, scroll toggle and keyboard are locked above; on top, a small extension of ours that numbers the links on demand ("hint mode", DOM-based, so it needs no accessibility tree). Search found no gamepad browsing extension for desktop Linux (Remapad's listing says Firefox for Android; Mozilla's spatial-navigation "SNAV" page is a plan).
7. *Video.* Software only until the Cedrus series is backported and a V4L2-request user exists (GStreamer's v4l2codecs, which WebKit uses, or a patched ffmpeg): realistically 360-480p H.264. A hand-off to a player (mpv with yt-dlp) for sites whose own player is too heavy needs both added to the image. Hardware decode is its own project.
8. *Reader view* for articles, and honest expectations: text sites, wikis, forums and search should be fine; heavy single-page apps and high-resolution video will not be.
**Choosing the browser.** Shortlist: Firefox (official aarch64 build, policies for everything declarative) and Chrome (official aarch64 build, a DevTools port that makes scripted measurement easy); a WebKit browser only if both fail (recent Epiphany needs GTK 4 and libadwaita and Cog is a launcher without tabs or an address bar, from general knowledge; either way WebKit would have to be built). Decide by a measurement session on the device with the same settings for both: cold start, resident set (PSS, all processes) after eight fixed pages, scroll smoothness, load times, pressure-stall figures, battery, and the operator's own verdict ("bearable"), using the profiler already in `os/dev/`. **Open:** what the operator will actually browse (sets the page list and the weights), whether Google's Chrome is acceptable beside Firefox, and the one browser for 0.1.0.

## USB-C: power and data together (operator question 2026-10-11; read from the device tree and kernel config on the host, NOT yet tried on the hardware)
**What the board has.** The RG34XXSP's device tree wires the port to the H700's OTG controller (`musb`, `dr_mode = "otg"`) with an **ID-detect GPIO** (not a Type-C controller: there is no `typec`/PD node), a **GPIO-switched 5 V regulator** (`usb0-vbus`) that supplies VBUS when the board is the host, and the **AXP717** as the VBUS input/charger (`input-current-limit` 1.5 A, matching Anbernic's 5 V / 1.5 A). The kernel already has everything in software: MUSB dual-role, the gadget stack with configfs (NCM, ECM, RNDIS, EEM, mass storage), USB Ethernet adapters as modules (RTL8152, AX88179, CDC), USB storage/UAS/HID, the AXP20x charger.
**1. Charging while connected to a computer (device mode): feasible.** Plugged into a PC the port is a sink: VBUS charges the battery and the handheld can present itself as a USB Ethernet adapter (NCM works on Windows 11 and Linux; RNDIS for older Windows), so a computer can reach it by SSH/SFTP with no Wi-Fi at all, and the TF2 card can be offered as mass storage. Needs only userspace: a configfs gadget setup, an address (link-local or a tiny DHCP), and a desktop-mode toggle next to SSH. To verify on the device: the role switch happens when the cable is inserted, the charge current limit with a PC port (500 mA expected), and that the SSH toggle covers the USB interface.
**2. Host mode (a USB Ethernet adapter, a controller, a disk) while charging: NOT possible safely with the port as wired, without a hardware accessory and a software check.** In host mode the board drives VBUS itself from the 5 V regulator, so feeding external 5 V into the same pin (a charging hub or an OTG-plus-charge adapter) would back-feed that regulator: a kernel patch review for the sibling RG35XX 2024 board warns that the host controllers keep the 5 V enabled and that plugging into another power source can blow the board's regulator. A charge-through hub also relies on CC/PD signalling, which this port has no controller for. A safe version needs (a) a self-powered or charge-through hub, (b) the 5 V regulator off whenever external VBUS is present, which the PHY driver may already do (it reads the PMIC's VBUS-present state; NOT verified in the driver source), and (c) a bench test with a USB-C power meter. Until then: peripherals in host mode run on the battery, and charging uses the plain cable.
**3. Charging itself:** two reviews report cable trouble on this line (C-to-C cables, chargers); an adapter with a 5.1 k pull-down on the device side is the known remedy, which fits a port with no CC controller. Document "use the supplied A-to-C cable or a known-good one".
**Proposed work (after the sweep frees the device):** a `wisp-usb-gadget` oneshot (configfs NCM + a link-local address, started with the SSH toggle), then the bench tests above. Decision for the operator: whether USB networking is part of 0.1.0 (it is cheap) or later.
**Correction (2026-10-12, read from the built SYSTEM and `build/linux/.config`; nothing run on the device):** the image ALREADY ships ROCKNIX's `/usr/bin/usbgadget` (JELOS/ROCKNIX, GPL-2.0), `80-usbgadget.rules` and `usb-gadget.target`; the note above wrongly proposed writing the oneshot from scratch. What the script does: modes `disabled` / `network` (NCM, the handheld takes 169.254.170.2/16 and runs a one-lease `udhcpd` for the PC, Windows-NCM compatible id) / `file_transfer` (MTP via `umtprd`); `usbgadget --start` restores the mode saved in `/storage/.cache/usbgadget/usbgadget.conf`. It is started at boot by `rocknix-autostart` (`/usr/lib/autostart/common/081-usbgadget`), which effort 1 removes, so the gadget disappears with it unless started from our own unit. With no saved mode `--start` calls `usb_stop` + `set_role host` (gadget off, port host), and WispOS has no UI that picks a mode, so as built it is dormant. The device kernel has MUSB dual-role, `USB_ROLE_SWITCH`, configfs with NCM/ECM/RNDIS/EEM/mass storage/FunctionFS. Open (device): the script's cable detection (`is_cable_connected`) looks for a PHY supplier named like Rockchip's (`*usb2phy`); the H700 uses `sun4i-usb-phy`, so expect it to find nothing there (not checked), which also removes one of the four sensors in its `external_vbus_present` guard for host mode. **The port is either device or host, never both: "connect to a computer" (gadget) and the OTG host toggle are one three-way setting (off / computer / host), off at every boot.**

**DECIDED, GATED BY A SPIKE (operator, 2026-10-11: "the hard constraint is a spike; depending on its results we go forward or not"): a USB host (OTG) toggle in desktop mode's menu, built the safe way, next to the SSH toggle.** Nothing below is built until the spike (next section) passes. The safe way, as rules the implementation and its tests must satisfy:
1. **Off at every boot** (the state lives in RAM, not on the card). With it off the port is peripheral-only: the board never drives VBUS, so an OTG adapter or a charger plugged in by mistake cannot make it source 5 V. (Needs a way to force the role from software: the sunxi MUSB `mode` attribute or the PHY's forced mode is the candidate; NOT yet verified on this kernel.)
2. **On is refused while external power is present** (the AXP717 USB supply reports online): the menu says "unplug the charger first", it does not try.
3. **Auto-drop:** while host mode is on, if external VBUS appears (a charger or a charge-through hub is connected) the 5 V regulator is switched off at once and the port returns to peripheral; the toggle shows off again. A watcher on the power-supply uevent, not a poll.
4. **Battery floor:** host mode switches itself off below a battery level (proposed 15%), since peripherals run on the battery.
5. **No charge-through promises** until the bench test passes: a self-powered hub with passthrough charging, a USB-C power meter, and the back-feed check from item 3; the result goes in this document before the toggle ships in a release.
6. Tests: the rules above are a pure decision function (like `wisp-compat-gate`) with a table test; the on-device checks (forced role, regulator off on VBUS, meter readings) are gates for the release, not for the table test.
Together with the USB-networking gadget above (device mode: power and data from a computer), this gives both directions of USB use; host mode never charges, by design.

### Spike S-USB: can the host role be made safe on this board? (go / no-go for the OTG toggle)
**Question:** can software force the port into peripheral-only, refuse host mode while external power is present, and drop the 5 V output the moment external VBUS appears, with no moment where the board drives VBUS into a charger or a PC?
**Time box:** half a day of work once the device is free, in three phases; stop at the first failed criterion.
- **Phase 0 (host only, no hardware risk):** read the 7.2 kernel sources of record for `phy-sun4i-usb` (ID and VBUS detection, when the `usb0-vbus` regulator is enabled, what it does when the AXP717 reports VBUS present), `musb_sunxi` (the role/`mode` control) and the AXP717 USB power-supply driver (the `online` property and its uevent). Output: written answers to the three rules (force peripheral, refuse on external power, drop on VBUS), or "the kernel cannot do X".
- **Phase 1 (device, nothing plugged in):** read the live state: the MUSB `mode` attribute, `/sys/class/udc`, the regulator's state, the power-supply `online` flags; flip the role with nothing connected and read what changes. No cable, no risk.
- **Phase 2 (bench, the operator present, a USB-C power meter inline, a power bank or a current-limited source, never a wall PD charger):** T1 forced peripheral with an OTG adapter: the meter shows no VBUS output. T2 host on with a keyboard: 5 V and the device enumerates. T3 host on, then external power appears (a powered hub): the output drops within the time the rules require, no back-feed, the board stays cool. T4 external power present, then try to enable host: refused. T5 battery floor. Each of T1-T4 repeated for at least 10 plug/unplug cycles.
**Pass:** Phase 0 shows the kernel can do all three; T1-T4 pass every cycle; nothing warm or smelly. **Then:** build the toggle exactly as the six rules say. **Fail (any of: the role cannot be forced, the output stays on with external VBUS, a single back-feed in T3):** the toggle is dropped, and the finding is written down: today's hardware behaviour (an OTG adapter flips the port to host by itself) stays, with a documented warning never to combine it with a charging hub. That is also a result worth having, because that risk exists today with or without our toggle.
**Stop rule for Phase 2:** the first unexpected reading ends the session; no retries "to see".

#### Spike S-USB, Phase 0 results (read from our patched kernel source, `phy-sun4i-usb.c` with ROCKNIX's 0151 patch, which `kernel/patches/0151-phy-fix-OTG-host-mode.patch` applies; 2026-10-11, host only)
- **The 5 V output follows the ID pin.** On this SoC (`phy0_dual_route`) the role is decided only by the ID-detect GPIO: ID low = host (the PHY is routed to EHCI/OHCI and the `usb0-vbus` regulator is ENABLED), ID high = peripheral (routed to MUSB, regulator DISABLED). Patch 0151 makes `phy_set_mode` a no-op for dual-route SoCs ("the PHY mode is fully determined by the selected mux route"), so **there is no software knob to force peripheral at runtime** through the PHY or MUSB `mode`. **Rule 1 ("off" means the port cannot source 5 V) cannot be met by userspace on this kernel.**
- **Rule 3 (auto-drop when external VBUS appears) already exists in the kernel:** `sun4i_usb_phy0_id_vbus_det_scan` disables the internal VBUS regulator whenever the PMIC reports VBUS PRESENT (`usb0_vbus_power-supply` = the AXP717 USB supply), and the driver registers a power-supply notifier (`sun4i_usb_phy0_vbus_notify`) so a change on that supply schedules the scan: event-driven, no polling. Whether the AXP717 emits that event promptly is bench test T3. **Rule 2 (no 5 V while external power is present) is therefore already enforced below userspace**, whatever the toggle says.
- **The open physical question:** when the board itself is sourcing VBUS in host mode, does the AXP717 report VBUS PRESENT because of the board's own 5 V? If it did, the scan would switch the regulator off again right after enabling it, and host mode could never stay on. ROCKNIX ships host mode for the sibling RG35XX 2024 board, so it presumably works (the PMIC's input comparator may be isolated from the board's own 5 V), but that is a bench test (T2), not an assumption.
- **What that means for the toggle:** the kernel already protects against the dangerous case (back-feed). What it cannot do is make "off" real: an OTG adapter (ID grounded) powers the port as a host with or without our toggle. Options, each with its price: (A) a small PHY patch of ours adding a gate (a sysfs attribute that keeps the regulator off and treats ID as high), carried with the other ~20 kernel patches and offered upstream; (B) two device trees and a reboot to switch (safe, awkward); (C) no gate: keep stock behaviour, drop the toggle, document it. **Decision after the bench tests**, not before. If the spike says host mode is safe as it is, (C) is the honest outcome and the toggle becomes a non-feature.

#### Spike S-USB, Phase 1 results (device, 2026-10-11 ~17:50 device clock; a CHARGER was plugged in, so the host direction was NOT tried; read-only apart from one harmless write)
- State with a charger attached: `extcon0` (the PHY) `USB=1 USB-HOST=0`; the regulator `usb0-vbus` **disabled** (no users; its supply `boost` also disabled); `axp20x-usb` power supply `online=1 present=1`, VBUS 4.944 V; the UDC `musb-hdrc.5.auto` exists and the kernel mounts configfs (a gadget can be built); MUSB `mode` reads `b_idle`, `vbus` reads "Vbus on". #### Spike S-USB: correction to Phase 0, and what was built (2026-10-12; read from the source and compiled, NOT run on the hardware)
- **Correction.** Phase 0 above says rule 2 ("no 5 V while external power is present") is "already enforced below userspace". Reading `sun4i_usb_phy0_reroute()` again, that was too strong. On this dual-route SoC the VBUS regulator is enabled the moment the ID pin goes low, without the "External vbus detected, not enabling our own vbus" test that `sun4i_usb_phy_power_on()` applies on the other SoCs (it returns before reaching it here). The scan's "disable our regulator if VBUS is present" runs BEFORE the reroute and only acts on a regulator that is already on, and nothing rescans afterwards unless the PMIC raises a new event. So a charger that is already attached when an OTG adapter goes in (or arrives in the same scan) can leave the board driving 5 V into it. This is a reading of the code, not an observed failure; it is the hazard the RG35XX 2024 patch review warned about. **Until the bench test says otherwise: do not combine an OTG adapter with a charging hub on any image built before this patch.**
- **Decision (operator, 2026-10-12, "let's do that"): option (A), the kernel gate.** `os/boot/patches/0001-phy-sun4i-usb-host-gate.patch` (applied by `os/boot/build-kernel.sh` after ROCKNIX's series): (1) the PHY gets a `host_enable` attribute, default 0 at every boot; while 0 the ID pin reads as high, so the port stays a peripheral and `usb0-vbus` is never enabled whatever is plugged in; writing 0 later drops the host role and the 5 V through the normal scan, writing 1 lets the ID pin decide again; (2) `reroute()` gets the missing external-VBUS test. Compiled with `-Werror`. The file is `/sys/bus/platform/drivers/sun4i-usb-phy/<addr>.phy/host_enable`.
- **The tool.** `wisp-usb status|off|computer|host` (`os/rootfs/usr/bin/wisp-usb`) is the three-way setting, off at every boot, nothing remembered. `host` writes the gate only when no external power is present, the supply can be read and the battery is at least 15% (`WISP_USB_BATTERY_FLOOR`); it takes a running gadget down first and starts `wisp-usb-watch.service`. The watcher listens for power-supply uevents (netlink; plus a 60 s look at the battery, which may raise no event) and writes the gate back to 0 the moment external power appears, a supply cannot be read, or the battery falls below the floor, leaving a one-line note for the menu. `computer` builds the CDC-NCM gadget (device 169.254.170.2, one DHCP lease for the PC, a fixed device MAC so a PC asks Public/Private once) and `off` removes it all. A kernel without the gate attribute is told so and never offered host mode. ROCKNIX's `usbgadget`, its udev rule, boot hook and MTP daemon are pruned (its role switching goes round the gate and its cable detection is Rockchip-shaped). Tests: `os/test_wisp_usb.py`, 40 against a fake `/sys` and `/run`, 14 mutants of the rules all caught; the QEMU test checks the fail-closed behaviour on a kernel without the gate.
- **Release gate.** No release carries host mode before its bench result is recorded here: `check_release.py` has the row `usb_host_bench` (DIFFERS unless `usr/share/wispos/usb-host-bench` exists, which `stage_rootfs.py` writes from the build variable `WISP_USB_HOST_BENCH`, a one-line reference to the result below), and `make-release.py` refuses on any DIFFERS row.
- **Not built:** the desktop-mode menu entry that calls `wisp-usb` (desktop mode does not exist yet); Phase 2 itself.
