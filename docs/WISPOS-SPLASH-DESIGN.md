# WispOS boot splash: design

Requirement (operator, 2026-10-08, sharpened 2026-10-11): from power-on until either the first-time setup screen or the Steam login/home screen appears, the panel shows the **WispOS spinner** with a **one-line live stage status** and a **short advertised hint to toggle a live boot log** (like Tab on a normal Linux boot). It REPLACES today's boot screen (the ROCKNIX splash and the live scrolling log). The device state decides where it hands over: first run -> the setup screen, otherwise -> Steam. Failures are never hidden.

**LOCKED (operator, 2026-10-11): the splash in its centred black composition, and the first-run hand-over (3 s: 1.5 s fade out, 1.5 s fade in, black-to-navy gradient throughout, played once by the setup program).** Changes need the operator.
Status: **prototype written (`os/splash/`, in the setup screen's design language), host-tested (16 tests), cross-compiles static for aarch64 (860 KB stripped); boot integration verified in QEMU (2026-10-11, below); not on the device yet.**

**Design language (operator, 2026-10-11):** the splash is built from the first-time setup screen's components, not a design of its own: the same tokens (`os/ui/wisp-ui.h`), typeface (Liberation Sans, rendered into glyph atlases by `os/ui/gen_assets.py` from the files the setup screen loads), badge, round-dot spinner, key-pill hint and red "!" failure treatment. **One documented exception, the operator's call: a black ground and a single centred column** (logo, "WispOS", spinner, the stage below it), because the boot screen sits between black panels; see "Boot-time screens" in docs/WISPOS-UI-LANGUAGE.md. The setup screen that follows keeps the standard ground and grid.

## Where today's boot screen comes from (verified 2026-10-11 from our build)
- Our kernel embeds **ROCKNIX's reference initramfs, byte for byte** (`os/boot/build-kernel.sh`: `CONFIG_INITRAMFS_SOURCE=wispos-initramfs.cpio.gz` (a file in the kernel tree, named relatively so the Image does not carry the work directory's name), made from `ref-boot/ref.cpio.*`). Its `/init` (1380 lines of busybox shell) does the storage work we depend on (find BOOT by label, loop-mount `/flash/SYSTEM`, resize, overlays, modules) and draws the screen: `load_splash` runs `/usr/bin/rocknix-splash` (the logo), sets console fonts, prints "==> Loading, please wait...", progress lines and error countdowns to `/dev/console`.
- `extlinux.conf` has `console=tty0` and no `quiet` (`os/build-image.sh`, "so the first boots of a new image are readable"), so kernel and systemd text also lands on the panel; `CONFIG_LOGO=y` adds the kernel logo.
- The display stack is **built into the kernel** (`DRM_SUN4I`, `DRM_SUN8I_MIXER`, `DRM_FBDEV_EMULATION`, `FRAMEBUFFER_CONSOLE`, `BACKLIGHT_PWM`: all `=y`), `/dev/fb0` is `sun4i-drmdrmfb` 720x480 32 bpp. The buttons are `KEYBOARD_GPIO` (built in) and ROCKNIX's joypad driver.
- Timeline on the device: about 5.7 s kernel, 14 s userspace to `wispos.target`, then Steam 1 to 4 minutes to draw. U-Boot (the pinned DDR3 binary) runs before all of it.

## Feasibility: yes. Honest limits first
1. **The first ~5 s are black** (U-Boot SPL + DRAM + loading the kernel, then the kernel until init starts). The bootloader is a pinned binary; nothing of ours runs before the kernel. The first pixel we can draw is when our splash starts from the initramfs' init, expected 4 to 6 s after power-on. Not fixable without a custom bootloader (not planned).
2. **The toggle button works only once the joypad's input device exists.** The GPIO key driver is built in, so it is likely present when the splash starts; to be verified on the device (`evtest`), as is which key SELECT is (default 314, `BTN_SELECT`).
3. **A short flat-colour gap at the sway hand-over** (the display master changes hands), hidden by giving sway the same background colour and starting the overlay at once.

## Design
**How we take over with the smallest change.** Keep ROCKNIX's initramfs (its mounting logic works and is the part we should not rewrite). The delta is: (a) replace `/usr/bin/rocknix-splash` with our static `wisp-splash`, which forks into the background and keeps animating; (b) boot arguments, built by `os/build-image.sh`: release `... logo.nologo vt.global_cursor_default=0 quiet loglevel=3 systemd.show_status=true`, dev `... logo.nologo vt.global_cursor_default=0 wisp.dev`; both keep `console=ttyS0,115200 console=tty0` (the text still goes to the console, hidden behind the splash, which is what makes the toggle possible). `quiet loglevel=3` only keeps the kernel's early text off the panel until the splash starts (about 4 s in); `systemd.show_status=true` is there because `quiet` alone would hide systemd's own lines and the log you get with SELECT would be nearly empty. (Correction of the first draft of this document, which said `quiet` and nothing else.) A **dev image** is not quiet (kernel text on the UART and in the log view) and shows the red DEV BUILD mark; **the splash is on in both**. The off switch is `wisp.splash=off` on the `APPEND` line of `extlinux.conf`, which is on the FAT partition and editable on any PC (there is no separate `splash.conf`: nothing reads files at the moment the splash starts, the command line is what exists then).
**The toggle is the Plymouth trick, no extra code for the log:** `wisp-splash` puts the virtual terminal in `KD_GRAPHICS` (fbcon stops drawing text but the console keeps filling its screen buffer) and draws on `/dev/fb0` itself. The toggle button switches the terminal to `KD_TEXT`: the real console, with everything ROCKNIX's init, the kernel and systemd printed, appears and keeps updating live; the button again returns to the spinner. Limit: the text view shows the console's screen buffer (the last ~30 lines), not unlimited scrollback.
**What it shows** (720x480, 32 bpp, on black): the badge centred at the top, "WispOS" in Title under it, the round-dot spinner (12 steps a second, about 1-2% of one core expected) centred below, the current stage in Body below the spinner, an optional Small dim detail line ("This can take a few minutes the first time."), and at the bottom the centred key-pill hint "SELECT  Boot log"; "DEV BUILD" in red at the very top on development builds. In the log view the console owns the screen; before switching, the splash prints one line on it ("Press SELECT to go back to the WispOS boot screen").
**Status line** = the stage the boot is in, from a FIFO (`/run/wisp-splash.fifo`, lines: `status TEXT`, `hint TEXT`, `fail TEXT`, `log on|off|toggle`, `ready`, `quit`). Fed by (i) the splash itself in the initramfs phase (it can read `/proc/mounts`: BOOT mounted -> "Reading the system", `/sysroot` mounted -> "Starting WispOS"), (ii) `wisp-splash-say "TEXT"` called by our units (`ExecStartPre=`): "Network", "Display", "Starting Steam", "Almost ready", (iii) `wisp-steam-watch`, which already knows Steam's start stages. A missed stage just keeps the previous line.
**Phases and hand-over (the hard part).**
- Phase A, framebuffer: from the initramfs until sway starts. `wisp-splash` draws on `/dev/fb0`.
- Phase B, Wayland: when sway takes the display the fb0 picture disappears and Steam needs minutes to draw, so the same renderer runs as a fullscreen Wayland client (shared-memory buffer, same pixels) from `sway`'s first `exec`, with sway's background set to the same colour so the gap is a flat colour for a fraction of a second. It exits on `ready`.
- End conditions by device state: **first run** (no Wi-Fi/setup done): `ready` is sent when the setup screen is mapped; **normal boot**: when Steam's window is presented (we already detect that from sway's tree, `wisp-steam-watch`). Whichever comes first for the state the device is in; never both.
**Never hide failures.** The splash reveals the log by itself (a) if the init or a unit reports `fail` (the line turns red first, then the log appears after 2 s), (b) if the boot has not reached `wispos.target` within 90 s, (c) if Steam has not shown a window after 6 minutes (the status line says "Steam is taking long", the hint says how to see the log). A boot failure must leave the same text on screen that ROCKNIX's init shows today.
**Off switches:** `wisp.splash=off` on the kernel command line (edit `extlinux.conf` on any PC); holding a button when power is applied is NOT possible (the first 5 s are before us). Dev images keep the splash on.

## Build and test
- Source `os/splash/wisp-splash.c` (static C, libc + libm, no SDL), tokens `os/ui/wisp-ui.h` (committed), assets `wisp-ui-assets.h` generated at build time by `os/ui/gen_assets.py` (glyph atlases at the four sizes and the badge, from the image's `/usr/share/fonts/liberation/LiberationSans-{Bold,Regular}.ttf` and `os/setup/assets/wispos-badge.png`; about 0.5 MB of source, not committed). Static aarch64 build: `aarch64-linux-gnu-gcc -O2 -static -I os/ui -I <gen> os/splash/wisp-splash.c -lm` (860 KB stripped; the initramfs grows by about 400 KB compressed).
- `os/setup/wisp-setup.c` now includes the same header (its colours, radius and panel geometry are the tokens; its values are unchanged), checked with a syntax-only compile against the pinned SDL headers; its renders are unchanged by construction but were not re-rendered (needs the emulated VM): re-render `os/setup/design/*.png` on the next VM session and diff them.
- Host test `os/test_splash.py` (16 tests): compiles the program, runs it against a **file-backed fake framebuffer**, and checks pixels: tokens equal the language document and the setup screen has no private palette; the ground is black and every element (badge, name, stage, detail, hint, spinner) is horizontally centred to within 4 px; the stage is below the logo and the key pill at the bottom centre; the spinner is the ring of round dots and moves; commands change the stage, detail and hint; a failure is the red-disc screen, stops the spinner and opens the log by itself after 2 s; the log toggle replaces the screen and returns; `ready` exits cleanly; long text is cut inside the panel; a tiny canvas never writes outside the buffer. `WISP_SPLASH_PREVIEW=DIR` writes PNGs for a human look.
- The first-run hand-over (3 s, fade out then fade in, a black-to-navy gradient throughout, once only) is specified in docs/WISPOS-UI-LANGUAGE.md and previewed by `os/splash/preview_handover.py`. The SETUP program plays it (an `--intro` mode, started with the splash's last frame as its first frame); the splash only has to end on a clean black frame and exit when the setup window is up. No Wayland overlay is needed for this transition (the Wayland phase is still needed to keep the splash up while Steam starts).
- **Boot integration, verified in QEMU (2026-10-11, `os/boot/qemu_splash_test.py`, PASS):** the initramfs delta is built (`os/boot/make-initramfs.sh`, `os/boot/patch_initramfs.py`: exactly the `rocknix-splash` entry replaced and `wisp-splash` added, 68 entries, tested on the real reference archive); a test kernel with it embedded boots the real test image on a 720x480 virtual GPU. Observed: the splash is on the panel 9.6 s after QEMU starts; the image's first boot resizes STORAGE and reboots once (`.please_resize_me` -> `fs-resize.target`, as ROCKNIX does), so the splash is seen twice on a fresh card with a black gap between; the daemonised splash **survives `switch_root`** (init moves `/dev` itself, `mount --move /dev /sysroot/dev`, so `/dev/wisp-splash.fifo` is the same pipe, inode checked); a `status` line written to it from the running system changes only the stage line of `/dev/fb0`; `ready` makes the process exit. Read `/dev/fb0` over ssh for a screenshot: it shows the splash's picture even when sway has taken the display.
- Seen in the same run and still open: (a) once sway starts the panel shows black until the setup/Steam window is up (about 50 s under emulation): that is the Wayland phase, not built; (b) nothing sends `ready` yet, so the daemon keeps drawing after sway has the display (wasted CPU, must be fixed together with `wisp-splash.service`); (c) the first-boot resize reboot has no stage text of its own ("Preparing the card" would fit); (d) serial output is silent with `quiet`, so QEMU tests must use ssh, not the serial log, to know the guest is up.
- **Wired into the image (2026-10-11, host-tested by `SplashWiringTests` in `os/test_rootfs.py`, not yet built into an image):** boot arguments as above; `/usr/bin/wisp-splash-say` (`TEXT`, `--ready`, `--fail TEXT`; opens the FIFO read-write so it never blocks or fails a unit); a `sway.service` drop-in that says "Starting the display"; `wisp-setup.service` sends `--ready` right after the compositor's socket exists (**interim**: the framebuffer picture is hidden once sway owns the display, so the splash has nothing left to do; the Wayland phase will keep a boot screen up from here until Steam's window or the setup screen is mapped); the wrapper passes `--reveal-after 90` (the log opens by itself if nothing has ended the splash after 90 s).
- Still to do from the first version of this list: **nothing but the device** (the Wayland phase and the setup `--intro` are built, see the next section; the rebuilt kernel/SYSTEM/image and the QEMU boot of the whole chain are part of the release candidate's checks).
- On the device: screenshot by reading `/dev/fb0` (grim cannot see fbdev); CPU of the splash over a full boot; the hand-over checked 8+ times (the Steam UI's start stalls are intermittent: measurement discipline from the notes applies).

## The Wayland phase and the first-run hand-over (built 2026-10-12; host- and compositor-tested, NOT run on the handheld)
**Why:** the framebuffer splash is hidden the moment sway takes the display, so the panel was black from then until Steam's or the setup screen's first window (about 100 s in the field). The requirement above (spinner, one-line stage, boot-log hint "until the setup screen or the Steam home screen appears") is only met if something keeps the screen up.

**One drawing, three programs.** `os/splash/scene.h` holds the canvas and the setup screen's components (badge, round-dot spinner, text from the generated glyph atlases, key pill, the failure screen, the log view); `wisp-splash.c` (the initramfs, static), `wisp-bootscreen.c` (below) and `os/setup/bootframe.c` (the hand-over) include it, so they cannot drift apart. `os/splash/evinput.h` is the shared SELECT scanning.

**`wisp-bootscreen`** (`os/splash/wisp-bootscreen.c`, unit `wisp-bootscreen.service`, `Type=notify`, `After=sway.service`, `Before=wisp-setup.service wisp-steam.service`, not required by anything): a layer-shell OVERLAY over the whole output (anchor all, exclusive zone -1, no keyboard, no input region, so it moves nothing and takes nothing) that draws the same screen, at the output's NATIVE pixels (buffer scale = the output scale: Game mode runs the panel at scale 2; a larger output gets the 720x480 scene centred on black). Status lines arrive on `/run/wisp-bootscreen.fifo` (`wisp-splash-say` writes to both screens' FIFOs; `--ready` goes to the framebuffer splash only, `--done` to this one only); SELECT (read straight from evdev) or `log on|toggle` shows the live boot log (`journalctl -b -f`); `fail REASON` shows the red screen and opens the log after 2 s; after 6 minutes without a window the words become "This is taking longer than usual" and name SELECT. It sends `ready` to the framebuffer splash and `READY=1` to systemd with its first frame. **It ends by itself when the compositor announces any window** (foreign-toplevel protocol), and on `done`/`quit`, SIGTERM, the layer surface being closed, the compositor going away, a ceiling of 20 minutes, or (no foreign-toplevel protocol: nothing says when to stop) 90 s; it removes its FIFO. `wisp.splash=off` turns it off, `wisp.dev` adds the red DEV BUILD mark.
Tests: `os/test_bootscreen.py` runs it against the image's own sway 1.11 (headless, qemu-user): every pixel outside the spinner equals the splash's own render of the same state (also at output scale 2, and on a larger output), the spinner turns, status lines, failure screen, log toggle, a window ends it (and is what is on the screen afterwards), it moves no window, `done`, SIGTERM (the screen returns to what was under it), the ceiling, the slow-start words, the off switch and dev mark, `ready` reaches the splash's FIFO, no display (exit 1), and the aarch64 build as the image gets it; 10 mutants of its rules are all caught.

**The hand-over (`wisp-setup --intro MARKER`, first run only).** 3 s, fade out THEN fade in (docs/WISPOS-UI-LANGUAGE.md, contract `os/splash/preview_handover.py`). The setup program starts it before its first screen unless the marker file exists, writes the marker when it ends (once only), tells the boot screen to say "Getting ready for setup / This only happens the first time." (best effort, never blocking), and ignores buttons until it is over. Its first frame is the boot screen's own picture (`bootframe.c`, the shared drawing code), the last is the setup screen exactly: **the setup layer is the SIGNED difference from the navy ground** (the first version of the preview clipped it at 0, which would have left the black key pills missing at the end and had them pop in when it ended; the preview and `os/setup/handover.h` now both use the signed form). `os/test_setup.py` proves the C arithmetic equals the contract bit for bit on thousands of random pixels; `os/test_setup_render.py` RUNS the aarch64 setup program under qemu-user with SDL's dummy driver and checks that the list screen equals `design/list.png` pixel for pixel, that every `--demo handover:T` frame equals the independent composition (the splash's render and the list render mixed by the contract), that the intro plays once and writes its marker, and that the symbols page stays inside the panel (the old layout reproduced as a mutant).
**On the device, to look at:** the black gap between the framebuffer splash and the Wayland screen at sway's start (sway needs a moment; the screen is black until the boot screen's first frame, typically 1-2 s); the scale-2 → 1 → 2 changes `wisp-setup.service` makes around the setup screen (the boot screen re-draws at each); whether the hand-over's last frame and the setup screen's first normal frame are indistinguishable on the real panel; CPU of the boot screen over a full boot (it redraws only the spinner, 12 times a second).
